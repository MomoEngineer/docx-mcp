# 0007 – Phase 6 Module Layout: `footnote_edit.py`, Multi-Part Atomic Writes, and Anchor/Content Rules for `add_footnote`/`edit_footnote`

- **Status:** Accepted
- **Date:** 2026-09-15

## Context

[Roadmap.md, Phase 6](../../Roadmap.md#phase-6--footnote-editing-add_footnote-edit_footnote) requires extending `word/footnotes.xml`, the relationship wiring, and the in-text anchor "consistently" when a footnote is added or edited, keeping footnote IDs unique and valid; its Definition of Done requires a newly added footnote to be discoverable and correctly anchored via `get_footnotes`, and an edited footnote's content to update without breaking its anchor or ID.

[ADR-0005](0005-phase-4-text-edit-module-and-atomic-write.md)'s Consequences section deferred exactly this phase's central question: whether Phase 6 "reuse[s] `atomic_write_part` as-is, or need[s] a variant that writes more than one part in a single atomic step (`atomic_write_part` deliberately does not attempt multi-part atomicity ... since Phase 4 never needs it)." Phase 6 reaches that question: `add_footnote` must add a `w:footnoteReference` to `word/document.xml` *and* a matching `<w:footnote>` to `word/footnotes.xml` — and, when the target document has no footnotes yet, must also add a `[Content_Types].xml` `Override` and a `word/_rels/document.xml.rels` `Relationship` that don't exist yet either. Two sequential single-part `atomic_write_part` calls would leave a window (a crash between them) where `document.xml` references a footnote id `footnotes.xml` doesn't declare, or vice versa — exactly the "consistently" requirement Roadmap Phase 6 names.

Neither Roadmap.md nor README.md fixes how precisely the new footnote reference must be positioned within its anchor paragraph, whether the caller or the server allocates the new footnote's id, or what happens to an edited footnote's existing internal formatting. These were resolved as part of this ADR, in consultation with the project owner (the paragraph-level anchor granularity below was chosen deliberately over a character-offset alternative that was seriously considered — see Alternatives).

## Decision

1. **A new module `src/docx_mcp/footnote_edit.py`** owns both `add_footnote` and `edit_footnote`'s logic, the same phase-scoped exception to [docs/repository-structure.md §2](../repository-structure.md#2-conventions)'s one-module-per-tool convention already established by `text_edit.py` ([ADR-0005](0005-phase-4-text-edit-module-and-atomic-write.md)) and `paragraph_edit.py` ([ADR-0006](0006-phase-5-paragraph-edit-module-layout.md)): both tools share one "build a footnote's paragraph content from a `content` string" builder and one "look up a declared footnote by id in `word/footnotes.xml`" resolution, the same shared-addressing/algorithm merge criterion ADR-0006 fixed (not merely "same Roadmap phase").

2. **A new `atomic_write_parts(docx_path, parts: dict[str, bytes], *, max_size_bytes=...)` is added to `ooxml.py`, alongside `atomic_write_part` (unchanged).** It rewrites a `.docx`'s zip archive with every part named in `parts` set to its given bytes — **added** to the archive if not already present, **replaced** if it is — while every other existing part is copied through with its decompressed content and `zipfile.ZipInfo` metadata unchanged, using the same temp-file-in-`docx_path.parent`-then-atomic-`os.replace` sequence `atomic_write_part` already established. This mirrors `ooxml.py`'s existing `read_part`/`read_optional_part` pairing (`read_part` requires the part to exist, `read_optional_part` tolerates its absence) with the same strict-vs-permissive split, now for writes: `atomic_write_part` keeps its existing "the part must already exist" validation and its existing test suite completely unchanged (`add_footnote` is the only caller of the new function; `edit_footnote`, `find_text`/`replace_text`, and `insert_paragraph`/`delete_paragraph` keep using `atomic_write_part` as before). Both functions share one private helper that does the actual temp-file-assemble-and-replace work, so the atomic-swap sequence itself is proven once, not twice.

3. **`add_footnote` takes `(path, paragraph_index, content)` and always appends the new footnote reference at the *end* of that paragraph's plain text** — no character-offset parameter. This was chosen over a `find_text`-style `(paragraph_index, offset)` point location (seriously considered, since README's tool-table wording, "attach a new footnote to **a location in the text**," reads more naturally as sub-paragraph precision) because **no read tool this project has, including `get_footnotes` itself, can report a footnote anchor more precisely than `paragraph_index`** — accepting a character offset on write that no read tool can ever confirm back would be a write/read asymmetry, not a real caller-facing capability. Paragraph-level anchoring also avoids the run-splitting complexity `text_edit.py` needed for spans, and, unlike a span, a point-insertion at an arbitrary offset can land inside a `w:hyperlink`/`w:ins`/`w:del`/`w:smartTag` container with no obviously-correct behavior (splice inside it, or break out of it first) — a real formatting-fidelity question `replace_text` never had to answer, since it only ever inserts replacement text into the span it just consumed, never at an independently-chosen point.

4. **The new footnote's id is always server-allocated, never caller-supplied.** `add_footnote` computes it as one more than the largest integer-parseable, non-negative `w:footnote/@w:id` already declared in `word/footnotes.xml` (or `1` if that part is absent or declares no such id), then defensively re-checks the candidate string against every existing id (however it's spelled) and increments past any collision — closing the (practically unreachable, but cheap-to-close) case of a hand-crafted document using non-standard id spellings. This matches Roadmap Phase 6's "keeping footnote IDs unique and valid" as a server responsibility, not a caller one — the same posture `insert_paragraph`/`delete_paragraph` already take toward `paragraph_index` validity (server-checked, not caller-negotiated) and `replace_text`/`delete_paragraph` take toward staleness (server-verified, never caller-trusted).

5. **When the target document has zero footnotes (`word/footnotes.xml` absent), `add_footnote` creates it from scratch**, containing Word's two boilerplate footnotes (`w:id="-1"` `type="separator"`, `w:id="0"` `type="continuationSeparator"`) plus the one new real footnote, together with the `[Content_Types].xml` `Override` (`PartName="/word/footnotes.xml"`, the standard WordprocessingML footnotes content type) and the `word/_rels/document.xml.rels` `Relationship` (the standard footnotes relationship type, `Target="footnotes.xml"`) that make the new part a properly-wired OPC package member — mirroring exactly what `tests/fixtures/generate_fixtures.py`'s `_splice_in_footnotes` dev-tooling already does by hand-editing XML, now as production code reachable from a real tool call. `[Content_Types].xml` missing entirely is treated as an invalid document (`InvalidDocumentError`) — it is OPC's own mandatory root part, more fundamental than `word/document.xml`, and no valid `.docx` can lack it. `word/_rels/document.xml.rels` missing entirely is valid OPC (a source part with zero relationships may omit its `.rels` part) and is created fresh, containing only the new relationship, when needed. Before adding either the `Override` or the `Relationship`, existing entries are checked so a document already in a partially-inconsistent state (an `Override`/`Relationship` present despite the part itself being absent — not producible by this project's own tools, but not excluded either) is never given a duplicate.

6. **`edit_footnote` takes `(path, footnote_id, content, expected_content=None)` and rebuilds the target footnote's content entirely fresh from `content`, discarding whatever run/paragraph-level formatting the old content had.** `content.split("\n")` becomes one `w:p` per line — the exact inverse of `footnotes.py`'s existing `"\n".join(paragraph_plain_text(p) for p in paragraphs)` read-side convention (see Decision §8), so a round-trip through `get_footnotes` reproduces `content` verbatim; the first paragraph is prefixed with the same auto-number reference run (`w:r/w:rPr/w:rStyle w:val="FootnoteReference"` + `w:footnoteRef`) every real footnote's first paragraph carries. This was chosen over attempting a `replace_text`-style formatting-preserving text substitution because there is no well-defined "leftmost run" once the *number* of paragraphs itself may change (a one-paragraph footnote edited to two lines, or vice versa) — the same kind of ill-defined-interpolation problem [ADR-0005](0005-phase-4-text-edit-module-and-atomic-write.md)'s Alternatives already rejected for `replace_text`'s replacement-run formatting, one level up. `edit_footnote` only ever rewrites `word/footnotes.xml` — the anchor in `word/document.xml` and the id are both untouched — so it reuses plain `atomic_write_part`, not the new multi-part function.

7. **`edit_footnote` rejects `footnote_id` values `"-1"` and `"0"`** with a clear error. These are Word's reserved boilerplate separator/continuationSeparator footnotes, always present in any real `word/footnotes.xml` but never exposed by `get_footnotes` (population there is anchor-driven, per [ADR-0004](0004-phase-3-footnote-module-and-shared-anchor-resolution.md)) — a caller has no legitimate way to learn these ids exist through this project's own tools, so accepting them here would only ever serve an out-of-band attempt to corrupt Word's own separator rendering.

8. **`footnotes.py` gains an exported `render_footnote_content(footnote: etree._Element) -> str`**, its existing inline `"\n".join(paragraph_plain_text(p) for p in footnote.findall("w:p", ...))` logic (previously private inside `_content_by_id`) factored out so `footnote_edit.py` can compute `edit_footnote`'s returned `previous_content` from the exact same rendering `get_footnotes` uses, rather than a second, independently-consistent copy of it — the same "shared implementation, not independently-consistent ones" reasoning [ADR-0004](0004-phase-3-footnote-module-and-shared-anchor-resolution.md) already established for anchor-finding. This is a behavior-preserving refactor, verified by re-running Phase 3's existing `get_footnotes` test suite unchanged.

9. **`add_footnote` takes no staleness parameter; `edit_footnote`'s `expected_content` is optional, mirroring `delete_paragraph`'s `expected_text`.** `add_footnote` is a pure addition with nothing to lose, the same reasoning that gives `insert_paragraph` no staleness check. `edit_footnote` overwrites existing content wholesale with no way to reconstruct the original from `add_footnote` alone — the same "destructive and hard to undo" category `delete_paragraph`'s `expected_text` ([ADR-0006 §Decision.7](0006-phase-5-paragraph-edit-module-layout.md)) was introduced for, so it gets the identical optional-staleness-check shape rather than a new one.

## Alternatives

- **`add_footnote` accepting a `(paragraph_index, offset)` point location**, matching `find_text`/`replace_text`'s addressing shape exactly. Rejected in Decision §3: no read tool can report an anchor at that precision, so it would be write-only precision no caller could ever verify, and it reopens the hyperlink/tracked-change-boundary ambiguity `replace_text` closes only because it is always given a span it just consumed, never an independently-chosen point. Confirmed with the project owner before deciding.
- **Caller-supplied footnote ids for `add_footnote`.** Rejected in Decision §4: pushes uniqueness/validity checking (Roadmap Phase 6's own explicit requirement) onto the caller, and risks a caller-supplied id colliding with an existing one or with Word's reserved `"-1"`/`"0"` boilerplate ids.
- **Reject `add_footnote` outright when `word/footnotes.xml` doesn't exist yet, requiring some other setup step first.** Rejected: there is no other tool in this project's surface that could ever create that part, so this would make `add_footnote` unusable on the (extremely common) case of a document that simply has no footnotes yet — directly contradicting Roadmap Phase 6's own purpose.
- **Two sequential `atomic_write_part` calls** (one for `word/document.xml`, one for `word/footnotes.xml`) instead of a genuine multi-part atomic write. Rejected: reintroduces exactly the partial-state risk [docs/security-model.md §3](../security-model.md#3-atomic-write-contract) exists to close — a crash between the two calls leaves an anchor referencing a footnote that doesn't exist, or a declared footnote nothing references yet.
- **Extending `atomic_write_part` itself to accept either a single part or a dict**, instead of a second function. Rejected: would change its existing signature and, to stay permissive enough for `add_footnote`'s from-scratch case, would have to drop the "part must already exist" validation `test_ooxml_atomic_write.py::test_missing_part_is_rejected` already pins as intended behavior — silently loosening a currently-tested safety check of three other tools' write path for a capability only Phase 6 needs. A second function with its own, clearly-documented, more permissive contract avoids both problems, mirroring the existing `read_part`/`read_optional_part` split.
- **`edit_footnote` preserving the edited footnote's existing run-level formatting**, splicing new text into the old runs the way `replace_text` does for body text. Rejected in Decision §6: `replace_text` always operates on a span within a single, already-known paragraph's existing runs; `edit_footnote`'s `content` can change the *number* of paragraphs the footnote has, for which "the old run's formatting" has no well-defined meaning once a paragraph is added or removed. Rebuilding fresh, with a content model that is the literal inverse of `get_footnotes`' own reading convention, is simple, predictable, and exactly round-trippable.
- **Allowing `edit_footnote` to target `"-1"`/`"0"`.** Rejected in Decision §7: these ids are never legitimately learned by a caller through this project's own tools; permitting them would only enable out-of-band corruption of Word's boilerplate separator rendering, for no legitimate use case.
- **Mandatory (not optional) `expected_content`.** Rejected for the same reason [ADR-0006](0006-phase-5-paragraph-edit-module-layout.md) kept `delete_paragraph`'s `expected_text` optional: needless friction for a caller with a freshly-read, known-fresh `footnote_id` (e.g. immediately after its own `add_footnote` call).

## Consequences

- **Positive:** `add_footnote`/`edit_footnote` get one implementation of "how a footnote's paragraph content is built from a string" and reuse `get_footnotes`' own content-resolution logic for `edit_footnote`'s return value, so none of the three tools can silently drift apart on what a footnote's content *is*. The multi-part atomicity gap [ADR-0005](0005-phase-4-text-edit-module-and-atomic-write.md) named as Phase 6's problem to solve is closed with a new, narrowly-scoped function that leaves every existing write tool's behavior and tests completely unchanged. The paragraph-level anchor-granularity decision keeps `add_footnote` free of the run-splitting/container-boundary complexity `text_edit.py` needed, at the cost of not matching README's phrasing quite as literally — recorded here, with the reasoning, as a deliberate, revisitable choice rather than an oversight discovered later.
- **Negative / Effort:** `add_footnote`'s from-scratch branch (creating `word/footnotes.xml`, `[Content_Types].xml`'s `Override`, and `word/_rels/document.xml.rels`'s `Relationship` together) is the most structurally involved write path in the project so far, needing its own dedicated test coverage (including the edge case of `word/_rels/document.xml.rels` being absent entirely, which no real fixture exercises — only a synthetic per-test archive can). `ooxml.py` now has two atomic-write entry points instead of one, a small increase in surface area, justified in Decision §2 by not weakening the existing one's tested guarantee.
- **Follow-up decisions:** Phase 7 (security hardening) will need to extend its path-traversal/atomic-write test sweep to cover `atomic_write_parts` alongside `atomic_write_part`; a future MINOR version of `add_footnote` could add an optional offset parameter if a real caller need for sub-paragraph anchor precision ever surfaces, without breaking the paragraph-level default this ADR fixes now.
