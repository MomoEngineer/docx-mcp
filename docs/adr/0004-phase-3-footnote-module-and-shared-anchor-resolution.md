# 0004 – Phase 3 Module Layout: `footnotes.py` and Shared Footnote-Anchor Resolution

- **Status:** Accepted
- **Date:** 2026-09-14

## Context

[ADR-0003](0003-phase-2-module-layout.md) split `document.py` into `ooxml.py` → `document.py` → {`structure.py`, `metadata.py`}, and explicitly deferred one question to this phase: "None of Phase 3's `get_footnotes` is decided here — it will need its own look at whether it extends `structure.py` (footnote anchors) or gets a fifth module, deferred to that phase's own ADR discussion if warranted."

[Roadmap.md, Phase 3](../../Roadmap.md#phase-3--footnotes-read-path-get_footnotes) requires a dedicated `get_footnotes` tool that lists every footnote's ID, its anchor paragraph, and its resolved content, and requires that `read_document`'s inline `[^N]` markers, `get_structure`'s footnote-anchor index, and `get_footnotes`'s own output all "resolve consistently against the same data" — including the case of two footnotes anchored in the same paragraph.

`structure.py`'s `get_document_structure` already builds a footnote-anchor index (`FootnoteAnchor(id, paragraph_index)`) by walking `word/document.xml`'s paragraphs for `w:footnoteReference` elements. `get_footnotes` needs that exact same anchor data, plus content resolved from a part `get_structure` deliberately never opens ([specs/get_structure.md §3](../../src/docx_mcp/specs/get_structure.md#3-output-schema): "`get_structure` never opens `word/footnotes.xml`"). Without a shared implementation, the anchor-walking loop (`for footnote_ref in paragraph.iter(_W_FOOTNOTE_REFERENCE): ...`) would exist twice, and "resolve consistently" would depend on two independent implementations happening to agree rather than being true by construction.

## Decision

1. **A new module `src/docx_mcp/footnotes.py`**, parallel to `structure.py`/`metadata.py`, owning `get_footnotes`'s logic — consistent with [docs/repository-structure.md §2](../repository-structure.md#2-conventions)'s "tool logic = one module" convention, and with how `structure.py`/`metadata.py` were added in Phase 2 rather than folded into an existing module.

2. **The footnote-anchor-walking loop moves into `document.py`** as a new exported helper, `find_footnote_anchors(body) -> tuple[tuple[str, int], ...]`, returning plain `(id, paragraph_index)` tuples — deliberately *not* `structure.py`'s `FootnoteAnchor` dataclass, whose docstring and shape are pinned to [specs/get_structure.md §3](../../src/docx_mcp/specs/get_structure.md#3-output-schema)'s public output schema. `document.py` already owns "the one place `w:p`/`w:t`/`w:tab`/`w:footnoteReference` traversal happens" per its own module docstring ([ADR-0003](0003-phase-2-module-layout.md)); this extends that ownership to anchor-finding, not just paragraph-text rendering. `structure.py` is refactored to build its `FootnoteAnchor` list from this shared helper instead of its own inline loop — a behavior-preserving internal change verified by re-running Phase 2's existing test suite unchanged, the same kind of move [ADR-0003](0003-phase-2-module-layout.md) already made when it split `document.py` itself. `footnotes.py` uses the same helper, combined with content it resolves independently from `word/footnotes.xml`.

3. **Population is anchor-driven, not `footnotes.xml`-driven**: `get_footnotes` returns one entry per `w:footnoteReference` actually found in the body (via `find_footnote_anchors`) — the same population and order `get_structure`'s index uses — not one entry per `w:footnote` declared in `word/footnotes.xml`. A footnote declared in `footnotes.xml` but never referenced anywhere in the body (Word does not normally produce this, but a hand-crafted or corrupted document could) is intentionally excluded. This is also why Word's own boilerplate separator/continuationSeparator footnotes (`id="-1"`/`id="0"`, always present in a real `word/footnotes.xml`, never referenced by a body `w:footnoteReference`) never need explicit type-based filtering — they simply never have an anchor.

## Alternatives

- **Extend `structure.py` with content resolution instead of adding `footnotes.py`.** Rejected: `get_structure`'s own spec states it never opens `word/footnotes.xml` — folding content resolution into it would either violate that documented boundary or require a parallel "structure-without-footnote-content vs. structure-with-it" split inside one module, working against the one-tool-one-module convention for no benefit over a dedicated module.
- **Have `footnotes.py` call `get_document_structure` and reuse its `.footnotes` field.** Rejected: `get_document_structure` also parses `word/styles.xml` for heading resolution and can raise on a malformed `styles.xml` — entirely irrelevant to `get_footnotes`'s purpose, and would make `get_footnotes` fail (or need special-casing) on a document whose styles are broken but whose footnotes are perfectly readable.
- **Keep the anchor-walking loop duplicated in both `structure.py` and `footnotes.py`.** Rejected: exactly the duplication [ADR-0001](0001-ooxml-library-and-module-layout.md) and [ADR-0003](0003-phase-2-module-layout.md) already named as the trigger for factoring out shared logic, now with a third would-be copy.
- **Move `structure.py`'s `FootnoteAnchor` dataclass itself into `document.py`, shared by both consumers.** Rejected: that dataclass's docstring and field set are part of `get_structure`'s public output contract ([specs/get_structure.md §3](../../src/docx_mcp/specs/get_structure.md#3-output-schema)), not a generic primitive; `footnotes.py` needs the same two fields plus `content`, so sharing the exact class would either force an unused `content` field onto `get_structure`'s output type or force `get_footnotes` to wrap/subclass a type it doesn't own. A plain tuple is the smallest shared contract that actually generalizes.
- **`get_footnotes` driven by `word/footnotes.xml` (list every declared footnote, look up its anchor).** Rejected: an orphaned declared-but-unreferenced footnote would then appear in `get_footnotes`'s output with no counterpart in `get_structure`'s anchor index, directly breaking Phase 3's "resolve consistently against the same data" requirement — and would additionally require explicit filtering of the separator/continuationSeparator entries that anchor-driven population excludes for free.

## Consequences

- **Positive:** `read_document`, `get_structure`, and `get_footnotes` now share one implementation of "how a footnote anchor is found," not three independently-consistent ones; `get_footnotes` can never disagree with `get_structure` on which paragraph anchors which footnote id, because both are built from the same call. Each tool's logic still has exactly one home module, consistent with `docs/repository-structure.md §2`.
- **Negative / Effort:** `structure.py` is refactored (its inline anchor loop replaced by a call to `document.py`) even though its own public behavior and tests must stay green — verified by re-running Phase 2's test suite unchanged after the refactor, mirroring the verification `document.py`'s own Phase 2 split already required.
- **Follow-up decisions:** none anticipated; Phase 6 (`add_footnote`, `edit_footnote`) will need its own look at whether it writes through `footnotes.py` or a new module, since it is a write path with different atomicity requirements this ADR does not address.
