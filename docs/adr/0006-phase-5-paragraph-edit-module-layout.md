# 0006 – Phase 5 Module Layout: `paragraph_edit.py` and Style-Inheritance Rules for `insert_paragraph`/`delete_paragraph`

- **Status:** Accepted
- **Date:** 2026-09-15

## Context

[Roadmap.md, Phase 5](../../Roadmap.md#phase-5--paragraph-level-structure-edits-insert_paragraph-delete_paragraph) requires whole-paragraph insertion and deletion — body text or headings — with an inserted paragraph "inheriting the style of its surrounding context," and requires `delete_paragraph` to remove a paragraph "without leaving orphaned references." Both requirements are stated at the goal level; neither Roadmap.md nor README.md fixes the exact parameter shape or the precise inheritance rule, and both were resolved as part of this ADR rather than left implicit in the implementation.

[ADR-0005](0005-phase-4-text-edit-module-and-atomic-write.md)'s Consequences section explicitly deferred this: "Phase 5 ... and Phase 6 ... each get their own module-layout ADR — whether they extend `text_edit.py`'s conventions, reuse `atomic_write_part` as-is, or need a variant that writes more than one part in a single atomic step." Phase 5 reaches that question first; Phase 6 (`add_footnote`/`edit_footnote`) is unaffected by the decisions below and gets its own ADR when it starts.

## Decision

1. **A new module `src/docx_mcp/paragraph_edit.py`** owns both `insert_paragraph` and `delete_paragraph`'s logic, mirroring the phase-scoped exception [ADR-0005 §Decision.1](0005-phase-4-text-edit-module-and-atomic-write.md) already established for `find_text`/`replace_text`: both tools address the *same* body-paragraph list by the *same* `paragraph_index` convention (0-based among top-level `w:body/w:p` children — identical population to `get_structure`/`find_text`/`replace_text`), and share one "resolve and validate a `paragraph_index` against the current paragraph list" helper. Splitting them into two modules would either duplicate that resolution/validation logic or force one tool's module to import the other's for no ownership benefit — the same reasoning ADR-0005 gave, not a new precedent. (Contrast [ADR-0003](0003-phase-2-module-layout.md), which *did* keep Phase 2's `get_structure`/`get_metadata` in separate modules: those two tools share no comparable addressing contract or algorithm, only a phase number — the merge criterion is shared addressing/algorithm, not "listed together in one Roadmap phase.")

2. **`atomic_write_part` (from `ooxml.py`, Phase 4) is reused unchanged.** Both tools rewrite only `word/document.xml`; deleting a paragraph that contains a `w:footnoteReference` deliberately leaves the corresponding `<w:footnote>` entry in `word/footnotes.xml` in place (see Decision §5) rather than touching a second part, so no multi-part-atomic variant is needed in this phase.

3. **Style-inheritance rule, fixed here so the spec, tests, and implementation cannot drift from each other or from a plain reading of "inherits the style of its context":**
   - `insert_paragraph` takes an explicit `heading_level: int | None` (1–9). Given, the new paragraph's `w:pPr` is built fresh, containing only `<w:pStyle w:val="HeadingN"/>` — independent of whatever the anchor paragraph's own style or local formatting is. This is the only way to *create* a heading; there is no "infer heading-ness from context" mode, because context-inference cannot express "insert a new heading into a run of plain body text," a case the README's "body text or heading" tool description explicitly promises.
   - `heading_level` omitted (`None`): the new paragraph is plain body text. If the anchor paragraph (see Decision §4 for which paragraph counts as "the anchor") is **not itself recognized as a heading** (via `document.py`'s existing `heading_level_from_style_prefix`/`paragraph_style_id` — the same built-in-`HeadingN`-id heuristic `read_document` already uses, deliberately **not** `structure.py`'s fuller `styles.xml`/`basedOn`-chain resolution — see Decision §4's rationale), its entire `w:pPr` element is deep-copied verbatim onto the new paragraph — not just the `w:pStyle` id, so local overrides (indentation, spacing, `w:numPr` list membership) carry over too, matching Principle 1's spirit that a caller-visible "inherits the style" promise should mean *actually* blending in, not just sharing a style name.
   - `heading_level` omitted **and** the anchor **is** recognized as a heading: the new paragraph gets **no** `w:pPr` at all (the document's implicit default paragraph style), rather than copying the heading's own `pStyle`. Copying it would silently turn a plain-body-text insertion into an unwanted second heading — directly contradicting the "body text **or** heading" choice the caller is presumed to have made by leaving `heading_level` unset. This is the one place this ADR's rule deliberately departs from a naively literal "always copy the anchor's `pPr`" reading of Roadmap Phase 5's wording, precisely because that literal reading breaks the Roadmap's own first fixture case ("insertion after a heading" — read together with the `README.md` promise that a plain body-text insertion remains possible everywhere, not only between two existing body paragraphs).
   - Run-level (character) formatting is **not** part of this inheritance: the new paragraph's text becomes a single `w:r`/`w:t` run with no `w:rPr` at all, regardless of the anchor's run formatting. "Style" in Roadmap Phase 5's sense is the paragraph style (`w:pPr`/`w:pStyle`), the same granularity `document.py`'s existing `style_id` concept already uses everywhere else in this project (`get_structure`'s `ParagraphEntry.style_id`, etc.) — not character-level bold/italic/font choices, which is `replace_text`'s already-established (`w:rPr`-copying) territory for edits to existing text, not a new-paragraph concern.

4. **"Anchor paragraph" is defined as:** the paragraph named by `after_paragraph_index` when given; when `after_paragraph_index` is `None` (insert at the very start), the paragraph currently at index 0, if the document has at least one paragraph; when the document has zero top-level paragraphs, there is no anchor and the new paragraph gets no `w:pPr` regardless of `heading_level` being unset (the fresh-`pPr`-for-a-requested-heading-level branch is unaffected, since it never depends on an anchor at all).

   Heading detection for this rule deliberately reuses `document.py`'s Phase-1 built-in-id heuristic, not `structure.py`'s fuller resolution, for two reasons: (a) it keeps `paragraph_edit.py`'s write path from having to open and parse `word/styles.xml` at all — no other write tool touches that part, and `atomic_write_part`'s one-part-per-call contract (Decision §2) stays true without a second read dependency; (b) it is the same boundary `specs/read_document.md`'s existing "Heading detection" limitation already documents and tests accept (a custom-named style that resolves to a heading level only through `styles.xml`'s `basedOn` chain, e.g. `tests/fixtures/structured.docx`'s `MySectionHeading`, is not recognized as a heading by this rule either) — not a new limitation invented for this phase.

5. **A deleted paragraph's footnote reference(s), if any, are not specially handled.** `delete_paragraph` removes the whole `w:p` element, including any `w:footnoteReference` descendants; the corresponding `<w:footnote>` entry in `word/footnotes.xml` is left in place, now unreferenced. This is consistent with `specs/get_footnotes.md §5`'s already-documented behavior that an orphaned, never-referenced footnote is excluded from `get_footnotes`' output — Word itself renders remaining footnotes' numbering from reference order, so an orphaned `<w:footnote>` entry causes no visible gap or corruption in the rendered document, only inert unused data in the archive. Actively removing it is left to Phase 6, once real footnote-editing infrastructure exists; rejecting the deletion outright was considered and rejected (see Alternatives) as unnecessarily blocking routine paragraph restructuring in a footnote-heavy (e.g. academic) document, for a purely cosmetic archive-tidiness gain.

6. **`delete_paragraph` rejects removing a paragraph whose `w:pPr` contains a `w:sectPr`.** A `w:sectPr` inside a paragraph's `w:pPr` marks that paragraph as the last paragraph of a document section (every section but the final one, which instead has its `w:sectPr` as `w:body`'s own last direct child, never inside any paragraph's `w:pPr` and therefore never touched by paragraph deletion at all); silently deleting such a paragraph would remove required section properties and produce a document Word cannot reliably reopen. This is a real structural-validity risk this ADR closes with a clear, testable rejection rather than an implicit, silent corruption — not something Roadmap Phase 5's text calls out by name, but squarely inside its "without leaving orphaned references" DoD criterion read broadly (a body missing required section properties is an orphaned/incomplete structure in the same sense a dangling reference would be).

7. **`delete_paragraph` takes an optional `expected_text: str | None`.** When given, it must equal the target paragraph's current `paragraph_plain_text` exactly, or the call fails with a clear "stale `paragraph_index`" error before anything is written — the same staleness-closing shape already fixed for `replace_text`'s `location`/`search_text` pair (see [specs/replace_text.md §7](../../src/docx_mcp/specs/replace_text.md#7-error-behavior)'s "stale location" row for the concrete contract, and [ADR-0005 §Decision.1](0005-phase-4-text-edit-module-and-atomic-write.md) for why re-verifying a caller-supplied location before writing was the reason `find_text`/`replace_text` were merged into one module in the first place), applied to whole-paragraph deletion, which is strictly harder to undo than a text replacement (there is no way to reconstruct the exact original XML of a deleted paragraph from `insert_paragraph` alone). Optional, not required, so a caller confident its index is fresh (e.g. immediately after its own `insert_paragraph` call) is not forced to re-supply text it already knows.

8. **`insert_paragraph`'s verbatim-`pPr`-copy branch (Decision §3, second bullet) always strips any `w:sectPr` child from the copy before attaching it to the new paragraph, dropping the `w:pPr` entirely if nothing else is left.** Found during a dedicated post-implementation verification pass (not anticipated at Decision §3's original write-up): a paragraph whose `w:pPr` contains a `w:sectPr` (a section-ending paragraph, the same one Decision §6 protects from deletion) is not itself recognized as a "heading" by the built-in-id heuristic, so inserting plain body text immediately after it fell into the ordinary verbatim-copy branch — which, before this fix, copied the `w:sectPr` onto the new paragraph too, duplicating the anchor's section properties (page size, margins, header/footer references, ...) and silently creating an unintended extra section break the caller never asked for. `w:sectPr` is a section-boundary marker, not stylistic formatting, so it is excluded from "the style of its context" in the same spirit Decision §3's heading-anchor exception already excludes a heading's `pStyle` from a plain-text insertion — both are cases where the naive "copy everything from the anchor" rule would carry over structural meaning the caller did not ask for, not just visual formatting.

## Alternatives

- **Absolute slot `position: int` (Python-`list.insert` semantics) instead of `after_paragraph_index`.** Rejected: it would introduce a second, differently-shaped paragraph-addressing convention alongside the `paragraph_index` one every other tool already uses (`find_text`, `replace_text`, `get_structure`, `get_footnotes`), and requires an off-by-one translation ("insert after paragraph 5" → `position=6`) at every call site reasoning in terms of an existing paragraph a caller just read about.
- **Raw `style_id: str | None` parameter instead of `heading_level: int | None`.** Rejected: it would let a caller reference any style name, including one absent from `word/styles.xml` (a formatting-fidelity risk with no validation short of opening `styles.xml`, which Decision §4 already deliberately avoids for the write path), and pushes OOXML style-id knowledge onto the caller that `heading_level` avoids entirely by staying at the same semantic level `get_structure`'s `heading_level` output already uses.
- **Always copy the anchor's `pPr` verbatim when `heading_level` is `None`, with no heading-detection exception.** Rejected in Decision §3/§4: it makes "insert body text after a heading" silently produce a second heading, breaking the Roadmap's own first fixture case and the "body text or heading" choice the caller is presumed to control via `heading_level`.
- **Reject `delete_paragraph` on any paragraph containing a footnote reference.** Rejected in Decision §5: no tool in this project can yet remove just the reference without removing the paragraph, so this would make many ordinary edits to a footnote-heavy document impossible until Phase 6 ships, for a purely cosmetic gain (`get_footnotes` already tolerates and excludes the resulting orphan).
- **Clean up `word/footnotes.xml` inside `delete_paragraph` itself.** Rejected in Decision §2/§5: expands this phase's scope into Phase 6's territory and would need a multi-part-atomic write variant `atomic_write_part` does not currently provide, for a tool this phase does not otherwise need to touch a second part at all.
- **Mandatory (not optional) `expected_text`.** Considered for maximal safety, symmetric with `replace_text`'s mandatory `search_text`. Rejected as needless friction for a caller with a freshly-obtained index (e.g. right after its own prior `insert_paragraph` call in the same conversation); `replace_text`'s `search_text` is mandatory because it is *also* the substring being replaced, not purely a safety check — `delete_paragraph` has no equivalent double duty for `expected_text`.
- **Reject `insert_paragraph` outright when the anchor carries a `w:sectPr`, mirroring `delete_paragraph`'s guard, instead of silently stripping it from the copy.** Considered as the more conservative response to the bug found in Decision §8. Rejected: unlike deletion (which would destroy the section properties entirely, with no way to recover them), inserting next to a section-ending paragraph loses nothing — the anchor keeps its own `w:sectPr` untouched; only the *new* paragraph must not also get a copy of it. Refusing the insert outright would needlessly block a common, harmless case (adding a paragraph right before or after a section break) for no safety benefit.

## Consequences

- **Positive:** `insert_paragraph` and `delete_paragraph` share one implementation of "resolve and validate a `paragraph_index`/`after_paragraph_index` against the current top-level paragraph list," so they cannot disagree on addressing. The style-inheritance rule is fixed once, here, with its trickiest cases (anchor is a heading, caller wants body text; anchor carries a `w:sectPr`, Decision §8) reasoned through explicitly rather than discovered as a bug during implementation or, worse, left as a silent behavior a future change could flip unnoticed. `delete_paragraph` reuses `replace_text`'s already-tested staleness-check shape rather than inventing a new one.
- **Negative / Effort:** The heading-detection reuse (Decision §4) means `insert_paragraph`'s context-awareness is bounded by the same built-in-id-only limitation `read_document` already has — a custom-named heading style is treated as an ordinary body paragraph for inheritance purposes. This is a documented, existing-precedent boundary, not new risk, but it does mean the boundary now shows up in two independent tools' specs instead of one. The `w:sectPr`-stripping rule (Decision §8) was found only during a dedicated post-implementation verification pass, not the initial spec-first design — recorded here as a reminder that "copy the anchor's `pPr` verbatim" needed a second, non-obvious carve-out beyond the heading-anchor case already anticipated up front.
- **Follow-up decisions:** Phase 6 (`add_footnote`/`edit_footnote`) gets its own module-layout ADR, including whether an eventual `word/footnotes.xml`-cleanup extension to `delete_paragraph` (explicitly deferred in Decision §5) is worth taking on then.
