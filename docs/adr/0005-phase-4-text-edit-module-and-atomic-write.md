# 0005 – Phase 4 Module Layout: `text_edit.py` and the Atomic-Write Contract

- **Status:** Accepted
- **Date:** 2026-09-14

## Context

[Roadmap.md, Phase 4](../../Roadmap.md#phase-4--precise-text-edits-find_text-replace_text) requires `find_text`/`replace_text` to locate and rewrite text Word may have split across multiple internal `w:r` runs, without altering the formatting of anything the edit doesn't touch, and requires `find_text`'s output to be usable as unambiguous input to `replace_text`. Both tools are scoped to literal-substring search over top-level body paragraphs only (`w:body/w:p` direct children — the same population `get_structure`/`get_footnotes` already use), matching `paragraph_plain_text`'s existing text-assembly rules; regex is explicitly out of scope (see [specs/find_text.md §5](../../src/docx_mcp/specs/find_text.md#5-limitations-non-goals)).

This is also the project's **first write-capable tool pair**. `docs/security-model.md §3` has specified the atomic-write contract (temp file in the same directory, then atomic replace; original only ever touched by that final step) since Phase 0, but no code implements it yet — every tool through Phase 3 only ever opened a `.docx` for reading.

[ADR-0004](0004-phase-3-footnote-module-and-shared-anchor-resolution.md) deferred exactly this question: "Phase 6 (`add_footnote`, `edit_footnote`) will need its own look at whether it writes through `footnotes.py` or a new module, since it is a write path with different atomicity requirements this ADR does not address." Phase 4 reaches that question first.

## Decision

1. **A new module `src/docx_mcp/text_edit.py`** owns **both** `find_text` and `replace_text`'s logic: offset-to-XML-node mapping, the run-splitting replace algorithm, and a `TextEditError` exception. This is a deliberate, phase-scoped exception to [docs/repository-structure.md §2](../repository-structure.md#2-conventions)'s "tool logic = one module" convention as applied so far (one module per tool): `find_text` and `replace_text` share one `TextLocation` addressing shape and one offset-computation rule, and `replace_text`'s core correctness requirement — re-verifying a caller-supplied location before writing — *is* "recompute what `find_text` would compute at those offsets, and compare." Splitting them into two modules would force either duplicating that offset logic or having one tool's module import the other's for no ownership benefit. Phase 5's and Phase 6's tool pairs get their own module-layout decision at their own ADR, exactly as ADR-0003 deferred Phase 3's layout to ADR-0004.

2. **A generic `atomic_write_part(docx_path, part_name, new_content, *, max_size_bytes=...)` is added to `ooxml.py`**, not a new module. It rewrites a `.docx`'s zip archive with exactly one named part's bytes replaced, into a temp file created in `docx_path.parent` (guaranteeing the final rename shares a filesystem/volume with the target), then atomically replaces the original. Every other part is copied through with its **decompressed content and `zipfile.ZipInfo` metadata (compression type, timestamp, external attributes) unchanged** — not a claim of bit-identical *compressed* byte streams, which would require fragile low-level access to `zipfile`'s internals and is stronger than what [docs/testing.md §2.3](../testing.md#23-formatting-fidelity-test)'s fidelity methodology ("comparing the OOXML of untouched parts before and after") actually checks. `ooxml.py` is the right home because it already owns "generic OOXML/zip plumbing... no WordprocessingML-specific rendering logic" ([ADR-0003](0003-phase-2-module-layout.md)), and because Phase 5 (`insert_paragraph`/`delete_paragraph`) and Phase 6 (`add_footnote`/`edit_footnote`) are also `word/document.xml`/`word/footnotes.xml`-rewriting write tools that need the identical zip-rewrite-and-atomic-replace sequence — one implementation, one simulated-crash test (`docs/security-model.md §5`), reused rather than re-proven per write tool.

3. **The run-splitting algorithm's key rules, fixed here so `find_text`/`replace_text` cannot disagree with each other or drift across future edits to either tool:**
   - A match/location is `(paragraph_index, start_offset, end_offset)`, a slice of `document.py`'s existing `paragraph_plain_text(paragraph)` — never `read_document`'s marker-annotated rendering.
   - Matching is left-to-right and non-overlapping; case-insensitive comparison uses same-length windowed comparison against the *original* text, never a whole-string `.lower()` pass (some Unicode case folding changes length, which would desynchronize offsets from the source text).
   - Offset-to-node mapping walks a paragraph in document order exactly as `document.py`'s internal traversal does: a `w:t` contributes `len(text)` characters, a `w:tab` contributes exactly one, everything else (including `w:footnoteReference`) contributes zero and can therefore never fall inside a match span.
   - A node fully inside the matched span is consumed entirely; a node with partial overlap at a boundary keeps its unmatched prefix/suffix **in place, in its original run, with that run's original, untouched `w:rPr`** (the element's `.text` is truncated in place, never cloned into a new run). Exactly one new run, carrying a **deep copy of the leftmost matched run's `w:rPr`**, is created to hold the replacement text (no run at all if the replacement is empty). The single-run trivial case is not special-cased — it falls out of the general prefix/replacement/suffix handling for free. A run is only ever deleted once it has no children left at all (so a run that happens to also hold a `w:footnoteReference` is never deleted by this logic).
   - A **global replace** (no `location` given) computes every match against the original, unmodified tree first, then applies them per paragraph in **descending offset order** (rightmost first), so an earlier, not-yet-applied match's offsets — computed against the original text — are never invalidated by a later-processed one to its right.
   - A match whose leftmost and rightmost involved runs sit under **different nearest special-container ancestors** (`w:hyperlink`, `w:ins`, `w:del`, `w:smartTag`, or no such ancestor at all) is **rejected** with a clear error rather than spliced across the boundary — text entirely inside one such container remains matchable (consistent with `paragraph_plain_text` already including `w:ins`-wrapped text as current content), but a match that would straddle *into or out of* one is a formatting-fidelity risk (e.g. silently growing or shrinking an apparent hyperlink) this project's Principle 1 does not accept implicitly.

## Alternatives

- **Separate `find_text.py`/`replace_text.py` modules**, matching every prior phase's strict one-module-per-tool pattern. Rejected: see Decision §1 — the two tools' shared offset contract would either be duplicated or force a cross-module dependency between two files with no clearer ownership split than keeping them together.
- **Fold the write-path logic into `document.py`.** Rejected for the same reason ADR-0003 kept `ooxml.py`'s zip plumbing out of `document.py`: `document.py` is the read-rendering module every read tool depends on; making it also own write mutation would blur "how a paragraph's text is assembled" (its actual charter) with "how a paragraph's XML is mutated," and would make every read tool's module transitively depend on write-path code it never needs.
- **A dedicated `writer.py` module for `atomic_write_part` instead of extending `ooxml.py`.** Rejected: `atomic_write_part` has exactly the same "generic, zero-WordprocessingML-knowledge zip plumbing" character as everything already in `ooxml.py` (`validate_and_open`, `read_part`, `parse_xml`); a separate module would only add a file to navigate without a clearer ownership boundary.
- **Replacement-text formatting: no `w:rPr` at all, or proportional/interpolated formatting across the match.** Rejected: dropping formatting silently contradicts Principle 1's spirit even for "new" text a caller would reasonably expect to inherit its surroundings' look; proportional interpolation has no well-defined rule when boundary runs' `rPr`s differ in kind (e.g. bold vs. italic) rather than degree. Leftmost-run-wins is simple, predictable without inspecting the document, and reduces to the correct trivial-case behavior for free.
- **Global replace via rescan-after-each-edit** instead of a fixed, pre-computed match list applied right-to-left. Rejected: if `replacement_text` itself contains `search_text` (e.g. `"cat"` → `"cats"`), a rescan can re-match the just-inserted text and loop or double-replace. Computing matches once against the untouched original guarantees "replace exactly the N occurrences that existed in the original document," a cleaner and more testable contract.
- **Allow a match to silently splice across a run-container boundary** (hyperlink/tracked-change), documenting it as an untested limitation instead of rejecting it. Simpler and smaller in scope, but accepts a real, easy-to-hit formatting-fidelity risk this ADR's Decision §3 declines in favor of a detected, clearly-worded error.
- **Bit-identical compressed-byte-stream copying** for untouched zip parts, via low-level `zipfile`/raw-offset access. Rejected: fragile, harder to keep `mypy --strict` clean, and stronger than the guarantee `docs/testing.md §2.3` actually needs or tests (decompressed-content equality).

## Consequences

- **Positive:** `find_text` and `replace_text` share exactly one implementation of "how a character-offset span maps onto XML nodes and back," so they cannot disagree on addressing — the same "shared implementation, not independently-consistent ones" reasoning [ADR-0004](0004-phase-3-footnote-module-and-shared-anchor-resolution.md) already established for footnote-anchor resolution. The atomic-write contract gets one implementation and one crash-simulation test, ready for Phase 5/6 to reuse without re-proving it. Every guarantee this ADR fixes (leftmost-`rPr`-wins, right-to-left global replace, run-container-boundary rejection, decompressed-content zip fidelity) is stated once, here, rather than re-decided ad hoc while implementing either tool.
- **Negative / Effort:** `text_edit.py` is a larger module than any Phase 2/3 tool-logic module, since it carries a nontrivial algorithm rather than extraction/rendering logic; the run-container-boundary rejection adds an error path and dedicated test not strictly required by Roadmap Phase 4's own wording, taken on as a deliberate formatting-fidelity safeguard.
- **Follow-up decisions:** Phase 5 (`insert_paragraph`/`delete_paragraph`) and Phase 6 (`add_footnote`/`edit_footnote`) each get their own module-layout ADR — whether they extend `text_edit.py`'s conventions, reuse `atomic_write_part` as-is, or need a variant that writes more than one part in a single atomic step (`atomic_write_part` deliberately does not attempt multi-part atomicity here, since Phase 4 never needs it).
