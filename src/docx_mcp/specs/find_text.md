# Tool Specification: `find_text`

> Written before the implementation, per [CONTRIBUTING.md §4](../../../CONTRIBUTING.md#4-workflow-spec--tests--docs--implementation).

---

## Metadata

| Field | Value |
| --- | --- |
| **Tool name** | `find_text` |
| **Version** | `1.0.0` |
| **Type** | Read |
| **Status** | Implemented |

---

## 1. Purpose

Search a `.docx` file's body for a literal piece of text — even when Word has split it across multiple internal `w:r` runs — and return every match as a stable, addressable location a following `replace_text` call can act on unambiguously, without the caller ever having to reconstruct run-level XML structure itself.

## 2. Input Schema

| Parameter | Type | Required | Description / Value range |
| --- | --- | --- | --- |
| `path` | `str` | yes | Filesystem path to a `.docx` file. Same resolution and sandboxing rules as `read_document` (see [specs/read_document.md §2](read_document.md#2-input-schema)). |
| `search_text` | `str` | yes | The literal text to search for. Matched as an exact substring — **not** a regular expression (see [Limitations](#5-limitations-non-goals)). Must be non-empty (see [Error Behavior](#7-error-behavior)). |
| `case_sensitive` | `bool` | no, default `true` | `true`: only exact-case matches are found. `false`: matched case-insensitively (Unicode-aware), but `matched_text` in the result always carries the text's actual, original casing — never `search_text`'s casing. |

JSON Schema, as actually generated by the MCP SDK from the function signature:

```json
{
  "type": "object",
  "properties": {
    "path": { "type": "string" },
    "search_text": { "type": "string" },
    "case_sensitive": { "type": "boolean", "default": true }
  },
  "required": ["path", "search_text"]
}
```

## 3. Output Schema

Sketch:

```json
{
  "matches": [
    {
      "location": { "paragraph_index": 2, "start_offset": 7, "end_offset": 14 },
      "matched_text": "receive",
      "paragraph_text": "Please receive this message."
    }
  ]
}
```

JSON Schema, generated by the MCP SDK from the `FindTextResult` model (Pydantic v2 nests `TextLocation`/`TextMatch` under `$defs`; the contract test checks the properties, field types, and required-ness below, not byte-exact equality, consistent with [specs/get_structure.md §3](get_structure.md#3-output-schema)):

```json
{
  "type": "object",
  "properties": {
    "matches": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "location": {
            "type": "object",
            "properties": {
              "paragraph_index": { "type": "integer" },
              "start_offset": { "type": "integer" },
              "end_offset": { "type": "integer" }
            },
            "required": ["paragraph_index", "start_offset", "end_offset"]
          },
          "matched_text": { "type": "string" },
          "paragraph_text": { "type": "string" }
        },
        "required": ["location", "matched_text", "paragraph_text"]
      }
    }
  },
  "required": ["matches"]
}
```

Field semantics:

- **`matches`** is a **flat list**, never grouped or keyed by `paragraph_index` — the same reasoning [specs/get_footnotes.md §3](get_footnotes.md#3-output-schema) already gives for its own flat-list choice: two matches in the same paragraph must appear as two separate entries, never silently collapsed. Order is document order, then left-to-right within a paragraph.
- **`location`** — `{paragraph_index, start_offset, end_offset}`. `paragraph_index` is 0-based among top-level `w:body/w:p` children, identical population and indexing to `get_structure`'s `paragraphs`/`get_footnotes`'s anchors. `[start_offset, end_offset)` is a half-open Python-style slice of that paragraph's `document.py`'s `paragraph_plain_text(paragraph)` — the same **marker-free** text `get_structure` exposes as `paragraphs[].text`, **not** `read_document`'s `"# "`/`"[^N]"`-annotated rendering (see [Limitations](#5-limitations-non-goals)). This exact shape is what `replace_text`'s `location` parameter accepts — a caller can pass `matches[i].location` straight through with no reshaping.
- **`matched_text`** — the actual substring found at `location`, in its original casing (identical to `search_text` when `case_sensitive` is `true`; may differ in casing only, never in content, when `case_sensitive` is `false`).
- **`paragraph_text`** — the full `paragraph_plain_text` of the paragraph containing the match — the "context" the README's tool-table entry promises, named explicitly rather than a generic `context` field.
- **Matching is left-to-right and non-overlapping**: after a match at `[start_offset, end_offset)`, scanning resumes at `end_offset`, not `start_offset + 1`. Searching `"aaa"` for `"aa"` finds exactly one match (`[0, 2)`), not two overlapping ones.
- **Zero matches is a normal, successful result** — `matches: []`, not an error (see [Error Behavior](#7-error-behavior); contrast with `replace_text`'s global-mode behavior on zero matches).

## 4. Assumptions and Preconditions

- Same as [specs/read_document.md §4](read_document.md#4-assumptions-and-preconditions): `path` resolves inside an allowed root, checked before the file is opened; the file is a valid ZIP containing at least `word/document.xml`.

## 5. Limitations (Non-Goals)

- **No regular-expression support.** `search_text` is matched as a literal substring only. This is a deliberate scope boundary, not a placeholder for a future flag: a caller-supplied pattern executed against untrusted-length document text is a real denial-of-service vector (uncontrolled backtracking, "ReDoS") in exactly the same threat category this project already hardens against for XML entity expansion (see [docs/security-model.md §4](../../../docs/security-model.md#4-input-validation)); adding regex would also require mapping capture groups back onto run-level offsets, a materially larger and separately-scoped problem. A future phase that adds pattern support would need its own ADR (e.g. a timeout-bounded engine or a restricted safe subset), not a quiet extension of this tool.
- **Top-level body paragraphs only.** Identical scope to [specs/get_structure.md §5](get_structure.md#5-limitations-non-goals) and [specs/get_footnotes.md §5](get_footnotes.md#5-limitations-non-goals): text inside a table cell (`w:tbl`/`w:tc`) is not searched and cannot be addressed by `paragraph_index`. Table-cell text search/replace would need its own addressing scheme and is a separate, later scope decision, not an oversight.
- **A match cannot span a paragraph break.** `read_document` joins paragraphs with `"\n"` only in its own rendering (`document.py`'s `extract_text`); that character does not exist in the underlying XML, and `paragraph_plain_text` never includes it. `find_text` operates strictly per-paragraph, so a `search_text` containing a literal `"\n"` can never match, and text that is contiguous only in `read_document`'s flattened output but split across two `w:p` elements is never found as one match.
- **Operates on marker-free text.** `search_text` is matched against `paragraph_plain_text`, the same text `get_structure` exposes — **not** `read_document`'s `"# "`-prefixed or `"[^N]"`-annotated rendering. A caller that copies a snippet straight out of `read_document`'s output including a heading marker or footnote marker will not find a match containing that marker, since it is not part of the document's actual text content.
- **List numbering is not computed** — same as [specs/read_document.md §5](read_document.md#5-limitations-non-goals).
- **Case-insensitive matching can miss a character whose lowercase form is longer than one code point.** `case_sensitive=false` compares same-length windows of the document text against `search_text`, never a whole-string case-fold first — deliberately, since some Unicode case folding changes length (e.g. Turkish `İ`, U+0130, lowercases to *two* code points, `i` + a combining dot above) in a way that would desynchronize match offsets from the text as given, corrupting `location`s `replace_text` is meant to act on safely. The consequence: searching case-insensitively for `"istanbul"` does **not** match `"İstanbul"` in the document text (verified: `_find_spans` finds only the plain-ASCII-cased occurrences of a mixed-casing sample, never the `İ`-prefixed one). This is a deliberate correctness-over-completeness trade-off, not an oversight, and is orthogonal to locale-specific casing (e.g. Turkish dotless `ı`/`i`, which are not case-equivalent under Unicode's locale-independent default casing this tool uses) being out of scope entirely.

## 6. Formatting & Safety Guarantees

- Read-only: `find_text` never opens the target file for writing and never modifies it.
- `path` is resolved and validated against the allow-listed roots, and a UNC network path rejected, before the file is opened — identical to [specs/read_document.md §6](read_document.md#6-formatting--safety-guarantees).
- `word/document.xml` is parsed with the same hardened `lxml` parser (`resolve_entities=False`, `no_network=True`) as every other tool (see [ADR-0001](../../../docs/adr/0001-ooxml-library-and-module-layout.md)).

## 7. Error Behavior

| Case | Behavior |
| --- | --- |
| `path` escapes all allowed roots / no allowed roots configured / UNC network path | Identical to `read_document` (see [specs/read_document.md §7](read_document.md#7-error-behavior)). |
| File does not exist, is not a file, is not a valid ZIP, exceeds the size limit, or is missing/malformed `word/document.xml` | Identical to `read_document` — these checks are shared, unchanged logic. |
| `search_text` is an empty string | Rejected with a clear error before any search is attempted — an empty needle has no well-defined non-overlapping match semantics. |
| `search_text` is not found anywhere in the document | **Not an error.** `matches: []`. |
| `word/document.xml` contains a DTD declaring an external entity | Parsed successfully; the entity reference is never resolved (same guarantee as `read_document`, see [specs/read_document.md §7](read_document.md#7-error-behavior)). |

## 8. Test Coverage

Reference: `tests/test_text_edit.py` (functional and error/edge at the `find_text_matches` level), `tests/test_find_text_tool.py` (contract, functional, error/edge at the MCP-protocol level), `tests/test_security.py` (path sandboxing, shared), `tests/integration/test_find_text_replace_text_consistency.py` (cross-tool: a returned `location` is valid input to `replace_text`).

- **Contract:** tool discoverable via `list_tools`; name, description, input schema, output schema, and version (`_meta`) match this spec.
- **Functional:** against `tests/fixtures/run_split.docx` (new, Phase 4) — an exact match split across two runs with different formatting; a match entirely within one run; a match spanning a `w:tab`; case-insensitive matching that preserves original casing in `matched_text`; three non-overlapping matches within one paragraph with correct offsets; a fourth match in a different paragraph; no match found (`matches: []`). A synthetic per-test document (following `tests/test_document.py`'s convention) covers: a match immediately adjacent to a footnote reference on both sides (reference itself contributes no offset and never appears in `paragraph_text`); non-overlapping-match semantics (`"aa"` in `"aaaa"` finds two matches, not three overlapping ones); a length-changing case fold (Turkish dotted capital İ) earlier in a paragraph not desynchronizing a later match's offsets; each of several differently-cased occurrences of the same word keeping its own original casing in `matched_text` under `case_sensitive=False`.
- **Error/edge:** path outside allowed roots; empty `search_text`; missing file; non-`.docx`/corrupt-ZIP input; missing `word/document.xml`; malformed `word/document.xml`; missing `<w:body>`; oversized file (plus a file at exactly the size limit, accepted); XXE-crafted `.docx` (external entity not resolved, no leaked content).

## 9. Examples

Against `tests/fixtures/run_split.docx` (see `tests/test_find_text_tool.py`), where paragraph 0's text "Please receive this message." has "receive" split across two differently-formatted `w:r` runs (bold "rec" + non-bold "eive"), with `DOCX_MCP_ALLOWED_ROOTS=/workspace`:

Request:

```json
{ "path": "/workspace/reports/run_split.docx", "search_text": "receive" }
```

Response:

```json
{
  "matches": [
    {
      "location": { "paragraph_index": 0, "start_offset": 7, "end_offset": 14 },
      "matched_text": "receive",
      "paragraph_text": "Please receive this message."
    }
  ]
}
```

`location` can be passed straight through as `replace_text`'s `location` argument — see [specs/replace_text.md §9](replace_text.md#9-examples), which replaces exactly this match.
