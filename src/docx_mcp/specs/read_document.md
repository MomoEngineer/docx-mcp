## 1. Purpose

Read a `.docx` file and return its full body text as a single string, with Markdown-style heading markers and inline footnote-anchor markers, so a calling agent gets structural context — not just flattened text — from a single call.

## 2. Input Schema

| Parameter | Type | Required | Description / Value range |
| --- | --- | --- | --- |
| `path` | `str` | yes | Filesystem path to a `.docx` file. May be absolute or relative; it is resolved (`..` segments and symlinks included) and then must fall inside one of the roots configured via `DOCX_MCP_ALLOWED_ROOTS`. No default — an empty/unset allow-list denies every path (see [docs/security-model.md §2](../../../docs/security-model.md#2-path-sandboxing-rules)). |

JSON Schema, as actually generated by the MCP SDK from the `path: str` parameter (source of truth for the contract test — checked for the properties below, not for byte-exact equality, since the SDK may add its own fields such as `title`):

```json
{
  "type": "object",
  "properties": {
    "path": { "type": "string" }
  },
  "required": ["path"]
}
```

Non-emptiness of `path` is enforced by `resolve_safe_path` (the tool's own logic), not by this JSON Schema — see [Error Behavior](#7-error-behavior). The SDK's function-signature-based tool registration does not offer a way to add `minLength` or `additionalProperties: false` without hand-writing a custom arguments model, which is not proportionate for a single `str` parameter; revisit if a future tool's input schema needs it for a specific documented reason.

## 3. Output Schema

Sketch:

```json
{
  "text": "string — full document body text, one paragraph per line"
}
```

JSON Schema, as actually generated by the MCP SDK from the `ReadDocumentResult` model (source of truth for the contract test):

```json
{
  "type": "object",
  "properties": {
    "text": { "type": "string" }
  },
  "required": ["text"]
}
```

- `text` is a single string. Paragraphs are joined with `"\n"`, in document order, exactly as they appear in `word/document.xml`.
- A heading paragraph (`w:pStyle` whose style id starts with `Heading`, e.g. `Heading1`) is rendered as `"#" * level + " " + text`, e.g. `"# Introduction"` for level 1, `"## Background"` for level 2. The level is the trailing digits of the style id.
- A footnote reference (`w:footnoteReference w:id="N"`) is rendered inline, at its exact position in the paragraph's run sequence, as `[^N]`. The footnote's *content* is not included here (see [Limitations](#5-limitations-non-goals)).
- An empty paragraph is rendered as an empty line (`""`).
- A manual tab character (`w:tab`) within a paragraph is rendered as a literal `"\t"`.
- Deliberately minimal for this phase: no paragraph index, no per-paragraph metadata, no document metadata. Those are Phase 2 (`get_structure`, `get_metadata`).

## 4. Assumptions and Preconditions

- `path` resolves inside an allowed root (see [docs/security-model.md](../../../docs/security-model.md)); checked **before** the file is opened.
- The file exists, is readable, and is a valid ZIP archive containing at least `word/document.xml`.
- **Validation is structural, not by extension or declared content type.** `read_document` accepts any file whose internals satisfy the check above, regardless of its file extension. In practice: legacy binary `.doc` (not a ZIP at all) and `.odt` (a ZIP, but without a `word/document.xml` part) are rejected as a byproduct of that check (see [Error Behavior](#7-error-behavior)); a `.dotx` template or `.docm` macro-enabled document — both genuinely WordprocessingML, structurally identical to `.docx` for this tool's purposes — is accepted like any other `.docx`, since `[Content_Types].xml`'s document-vs-template declaration is not inspected. This is a deliberate scope choice, not an oversight: rejecting a structurally-valid WordprocessingML file by extension alone would serve no correctness or security purpose this tool actually needs.

## 5. Limitations (Non-Goals)

- **Heading detection is style-id-based**, not style-hierarchy-based: only paragraphs whose `pStyle` id starts with `Heading` (Word's built-in heading styles, e.g. produced by "Heading 1"–"Heading 9" in the UI) are rendered as headings. A document using a custom-named style for headings (resolved only via `styles.xml`'s `w:name`/`w:basedOn` chain) is not recognized as a heading by this tool. Full style-hierarchy resolution is Phase 2's `get_structure`.
- **Table content is not extracted.** `read_document` only walks direct paragraph children of the document body; text inside a `w:tbl` is not included. Table-to-text rendering is Phase 2's `get_structure`.
- **Footnote content is not included**, only the inline anchor marker `[^N]`. Resolving `N` to its text is `get_footnotes` (Phase 3).
- **Endnotes are not surfaced** — out of scope for the whole tool surface (see [README.md](../../../README.md#available-tools), which lists footnotes only).
- **List numbering is not computed.** A numbered/bulleted paragraph's text is returned as-is; the actual list number/bullet (which Word computes from `numbering.xml` and prior siblings) is not resolved or prefixed.
- **Tracked changes:** deleted text (`w:delText`, inside `w:del`) is excluded, since it is not part of the document's current content; inserted text (ordinary `w:t` inside `w:ins`) is included. This tool does not surface *that* a change was tracked — only the resulting current text. Reviewing/accepting/rejecting tracked changes is out of scope for the whole project (see [README.md](../../../README.md#out-of-scope-for-now)).

## 6. Formatting & Safety Guarantees

- Read-only: `read_document` never opens the target file for writing and never modifies it. The formatting-fidelity guarantee (nothing an edit doesn't touch may change) is trivially satisfied because there is no edit.
- The path is resolved and validated against the allow-listed roots before the file is opened, and a UNC network path is rejected before that resolution is even attempted, so `path` can never make the server originate a network connection (see [docs/security-model.md §1–2](../../../docs/security-model.md#1-threat-model)).
- Every internal XML part is parsed with a hardened `lxml` parser (`resolve_entities=False`, `no_network=True`) so a crafted external entity in the `.docx` cannot read local files or trigger network access (see [ADR-0001](../../../docs/adr/0001-ooxml-library-and-module-layout.md), [docs/security-model.md §4](../../../docs/security-model.md#4-input-validation)).

## 7. Error Behavior

| Case | Behavior |
| --- | --- |
| `path` escapes all allowed roots, or `DOCX_MCP_ALLOWED_ROOTS` is empty/unset | Rejected before the file is opened, with a clear error naming the cause (not the resolved absolute path of a rejected traversal attempt, to avoid confirming filesystem layout to a probing caller). |
| `path` is a UNC network path (`\\host\share\...`) | Rejected immediately by lexical inspection, before any OS-level path resolution is attempted — canonicalizing such a path can otherwise trigger a real network round-trip to `host` (see [docs/security-model.md §1](../../../docs/security-model.md#1-threat-model)). |
| File does not exist, or is not a file | Clear "not found" error. |
| File is not a valid ZIP archive | Clear "not a valid .docx file" error. |
| Required part `word/document.xml` is missing from the archive | Clear "not a valid .docx file" error. |
| File size exceeds the configured maximum (`50 MiB` default) | Rejected before the archive is opened. |
| `.docx` contains a DTD declaring an external entity | Parsed successfully; the entity reference is never resolved, so it contributes no text to the result (no crash, no file/network access, no leaked content) — see Formatting & Safety Guarantees. |

## 8. Test Coverage

Reference: `tests/test_read_document_tool.py` (contract, functional, error/edge at the MCP-protocol level), `tests/test_document.py` (functional and error/edge at the `extract_text` level, including XXE hardening), `tests/test_security.py` (path sandboxing).

- **Contract:** tool is discoverable via `list_tools`; name, description, input schema, and version (`_meta`) match this spec.
- **Functional:** against `tests/fixtures/minimal.docx` (plain paragraphs, two heading levels, one footnote reference) — exact expected `text` string, including marker placement.
- **Error/edge:** path outside allowed roots; empty `DOCX_MCP_ALLOWED_ROOTS`; UNC network path (rejected fast, no network wait); missing file; non-`.docx`/corrupt-ZIP input; oversized file; XXE-crafted `.docx` (external entity not resolved, no local file content leaks into the result).
