## Metadata

| Field | Value |
| --- | --- |

| **Type** | Write |

## 1. Purpose

Replace literal text in a `.docx` file — either every occurrence in the document, or one specific occurrence identified by a `location` from `find_text` — without corrupting the formatting of any text the edit doesn't touch, even when the target text is split across multiple internal `w:r` runs. This is the project's first write-capable tool: it is the first to implement the atomic-write contract from [docs/security-model.md §3](../../../docs/security-model.md#3-atomic-write-contract).

## 2. Input Schema

| Parameter | Type | Required | Description / Value range |
| --- | --- | --- | --- |
| `path` | `str` | yes | Filesystem path to a `.docx` file. Same resolution and sandboxing rules as `read_document` (see [specs/read_document.md §2](read_document.md#2-input-schema)). |
| `search_text` | `str` | yes | The literal text to replace. Must be non-empty. Always required, in **both** modes — in location mode it is not merely descriptive, it is the exact value the tool re-verifies against the location before writing (see [Output Schema](#3-output-schema) and [Error Behavior](#7-error-behavior)). |
| `replacement_text` | `str` | yes | The literal text to substitute. May be the empty string (a pure deletion). No length constraint — may be shorter, equal, or longer than `search_text`. |
| `location` | `TextLocation \| null` | no, default `null` | `{paragraph_index, start_offset, end_offset}` — exactly the shape `find_text` returns per match (see [specs/find_text.md §3](find_text.md#3-output-schema)). **Presence or absence of `location` is the sole mode switch** — there is no separate "mode" or "global" flag, so no combination of parameters is ambiguous by construction: `location` given → replace that one occurrence, after re-verifying it still holds `search_text`; `location` omitted (`null`) → replace **every** occurrence of `search_text` found in the document. |
| `case_sensitive` | `bool` | no, default `true` | Same semantics as `find_text`'s parameter of the same name. Used both for global-mode matching and for the location-mode re-verification comparison. |

JSON Schema, as actually generated by the MCP SDK from the function signature (Pydantic v2 nests `TextLocation` under `$defs`):

```json
{
  "type": "object",
  "properties": {
    "path": { "type": "string" },
    "search_text": { "type": "string" },
    "replacement_text": { "type": "string" },
    "location": {
      "anyOf": [
        {
          "type": "object",
          "properties": {
            "paragraph_index": { "type": "integer" },
            "start_offset": { "type": "integer" },
            "end_offset": { "type": "integer" }
          },
          "required": ["paragraph_index", "start_offset", "end_offset"]
        },
        { "type": "null" }
      ],
      "default": null
    },
    "case_sensitive": { "type": "boolean", "default": true }
  },
  "required": ["path", "search_text", "replacement_text"]
}
```

## 3. Output Schema

Sketch:

```json
{ "replacements_made": 1 }
```

JSON Schema, generated by the MCP SDK from the `ReplaceTextResult` model:

```json
{
  "type": "object",
  "properties": {
    "replacements_made": { "type": "integer" }
  },
  "required": ["replacements_made"]
}
```

- **`replacements_made`** — `1` in location mode (a successful call always replaces exactly one occurrence; anything else is an error, see [Error Behavior](#7-error-behavior)), or the total count of occurrences replaced in global mode (always `>= 1` for a successful call — zero matches in global mode is itself an error, not a `0` result, see below).
- **Deliberately does not return post-edit locations.** A location is only ever valid against the document state it was computed from; returning one here would invite a caller to reuse it as if it were fresh, immediately reintroducing the staleness problem this tool exists to close. A caller that needs the new state calls `find_text`/`read_document`/`get_structure` again.

## 4. Assumptions and Preconditions

- Same as the read tools: `path` resolves inside an allowed root, checked before the file is opened; the file is a valid ZIP containing at least `word/document.xml`.
- This tool additionally requires the write path to succeed: `word/document.xml` is re-serialized after editing and the whole archive rewritten (see [Formatting & Safety Guarantees](#6-formatting--safety-guarantees)). A `.docx` that `read_document`/`find_text` can open successfully is assumed writable back out the same way; no additional precondition beyond filesystem write permission on `path`'s directory (needed for the atomic temp-file-then-replace sequence) is imposed.

## 5. Limitations (Non-Goals)

- **No regular-expression support** — same rationale as [specs/find_text.md §5](find_text.md#5-limitations-non-goals).
- **Top-level body paragraphs only** — same scope as `find_text`; a `location` addressing a table cell is not meaningful because no such `paragraph_index` exists.
- **A match/replacement cannot span a paragraph break** — same as [specs/find_text.md §5](find_text.md#5-limitations-non-goals).
- **Operates on marker-free text** — `search_text`/`replacement_text` are plain content, not `read_document`'s `"# "`/`"[^N]"` rendering; `replacement_text` is inserted as plain text, so a caller cannot use it to create a heading or a footnote reference — those remain `insert_paragraph`'s (Phase 5) and `add_footnote`'s (Phase 6) jobs respectively.
- **No tracked-change markup is created.** The replacement is a direct content edit — the matched text is removed and the replacement text inserted as ordinary, non-tracked content — consistent with every other tool in this project; recording the edit as a Word "tracked change" (`w:ins`/`w:del`) is out of scope for the whole project (see [README.md](../../../README.md#out-of-scope-for-now)).
- **A match spanning a run-container boundary is rejected, not silently allowed.** If the matched text's leftmost and rightmost runs sit under different nearest special-container ancestors (`w:hyperlink`, `w:ins`, `w:del`, `w:smartTag`, or no such ancestor for one side and one for the other), the call fails with a clear error rather than splicing across the boundary — see [ADR-0005](../../../docs/adr/0005-phase-4-text-edit-module-and-atomic-write.md) for the rationale (an undetected splice here risks silently growing or shrinking the apparent extent of a hyperlink or tracked-change block, a formatting-fidelity violation this project does not accept implicitly). Text entirely *inside* one such container (e.g. a whole tracked-change insertion) remains a normal, matchable/replaceable target.
- **Whitespace-only or fully-overlapping replacement loops are not specially detected beyond the global-replace ordering rule** — see [Formatting & Safety Guarantees](#6-formatting--safety-guarantees) for why a `replacement_text` that itself contains `search_text` still terminates correctly and predictably.

## 6. Formatting & Safety Guarantees

- **Atomic write:** the edit is written via `ooxml.atomic_write_part` — the new `word/document.xml` bytes are written to a temp file **in the same directory** as `path`, then the temp file atomically replaces the original. A crash or interruption at any point before that final replace leaves the original file byte-for-byte intact (see [docs/security-model.md §3](../../../docs/security-model.md#3-atomic-write-contract), [ADR-0005](../../../docs/adr/0005-phase-4-text-edit-module-and-atomic-write.md)).
- **Untouched parts are unchanged:** every zip part other than `word/document.xml` keeps byte-identical decompressed content and its original `zipfile.ZipInfo` metadata (compression type, timestamp, external attributes) — see [ADR-0005](../../../docs/adr/0005-phase-4-text-edit-module-and-atomic-write.md) for why this, not bit-identical compressed bytes, is the guarantee made and tested.
- **Untouched text/formatting within `word/document.xml` is unchanged:** a boundary run's unmatched prefix/suffix text keeps its original `w:rPr` element, mutated in place (truncated), never replaced or cloned; every paragraph not itself containing a match is byte-identical, XML-node-for-node, before and after the edit.
- **Replacement-text formatting:** the newly inserted run carries a deep copy of the **leftmost matched run's** `w:rPr` (or no run at all if `replacement_text` is empty) — see [ADR-0005](../../../docs/adr/0005-phase-4-text-edit-module-and-atomic-write.md) for the rationale.
- **Global-replace determinism:** all matches are located against the original, unmodified document first; replacements are then applied per paragraph in descending offset order (rightmost first). This guarantees exactly the occurrences present in the *original* document are replaced exactly once each, even when `replacement_text` itself contains `search_text` (no re-matching of freshly-inserted text, no drift in not-yet-processed offsets).
- Path resolution, sandboxing, and hardened XML parsing are identical to every other tool (see [specs/read_document.md §6](read_document.md#6-formatting--safety-guarantees)).
- **A `DOCTYPE`/internal DTD subset in the original `word/document.xml`, if present, is not re-emitted in the rewritten output.** Serialization writes only the edited element tree, not the original document's DOCTYPE declaration. This is never a real Word document's structure — Word never writes a DOCTYPE into any `.docx` part — so it is only ever seen in adversarial input (e.g. an XXE probe, see [docs/security-model.md §4](../../../docs/security-model.md#4-input-validation)); its entity declarations are already never resolved during the edit (same guarantee as every read tool), and its absence afterward is a deliberate consequence of the write path, not a formatting-fidelity gap — no legitimate document content depends on it.

## 7. Error Behavior

| Case | Behavior |
| --- | --- |
| `path` escapes all allowed roots / no allowed roots configured / UNC network path | Identical to `read_document`, checked **before** any write attempt. |
| File does not exist, is not a file, is not a valid ZIP, exceeds the size limit, or is missing/malformed `word/document.xml` | Identical to `read_document` — checked before any write attempt. |
| `search_text` is an empty string | Rejected with a clear error before any matching is attempted. |
| `location.paragraph_index` is negative or `>=` the document's top-level paragraph count | Clear "location references a paragraph that does not exist" error. Nothing is written. |
| `location`'s offsets are out of range for that paragraph's text (negative, beyond the paragraph's length, or `start_offset >= end_offset`) | Clear "location is out of range" error — distinct from staleness below: this is a structurally impossible location regardless of document content. Nothing is written. |
| `location` is structurally valid, but `paragraph_plain_text(paragraph)[start_offset:end_offset]` (compared under `case_sensitive`) does not equal `search_text` | **Stale location** error: the document has changed since the location was computed (e.g. an intervening `replace_text` call), or the location was never valid for this `search_text`. This is the core check that closes the `find_text` → `replace_text` race/hallucination window. Nothing is written. Note: passing a `case_sensitive` value inconsistent with the one used when the location was originally obtained can also trigger this error — an accepted, still-correct edge of the same check, not a separate error category. |
| `location` omitted and `search_text` is not found anywhere in the document | Clear "no occurrences of search_text found" error. **Not** a silent `{"replacements_made": 0}` — a caller must never be able to mistake "nothing changed" for "the edit succeeded." Nothing is written. |
| A match (in either mode) spans a run-container boundary (see [Limitations](#5-limitations-non-goals)) | Clear error naming the boundary case; nothing is written. In global mode, this aborts the whole call — no partial replacement is written — since "some but not all requested occurrences were replaced" is a worse silent-failure mode than refusing the whole edit. |
| The process is interrupted/crashes after the new `word/document.xml` content is computed but before the atomic replace completes | The original file is untouched — verified by a dedicated simulated-crash test (see [docs/security-model.md §5](../../../docs/security-model.md#5-testing-obligations)). |
| `word/document.xml` contains a DTD declaring an external entity | Parsed successfully; the entity reference is never resolved; the edit proceeds normally against the resulting (entity-free) text. |

## 8. Test Coverage

Reference: `tests/test_text_edit.py` (functional, formatting-fidelity, and error/edge at the `replace_text_in_document` level), `tests/test_ooxml_atomic_write.py` (the shared `atomic_write_part` helper, including the simulated-crash proof), `tests/test_replace_text_tool.py` (contract, functional, error/edge at the MCP-protocol level), `tests/test_security.py` (path sandboxing, shared), `tests/integration/test_find_text_replace_text_consistency.py` (a `find_text` location succeeds unmodified as `replace_text` input; reusing a location after an intervening edit is rejected as stale; `read_document`/`get_structure`/`get_footnotes` stay consistent with each other after a `replace_text` write).

- **Contract:** tool discoverable via `list_tools`; name, description, input schema (including the nested, optional `location` object), output schema, and version (`_meta`) match this spec.
- **Functional, location mode, against `tests/fixtures/run_split.docx`:** a match split across two differently-formatted runs (assert the exact resulting run structure: untouched-formatting prefix run, one new run with the leftmost run's formatting, untouched-formatting suffix run); a match entirely within one (non-default-formatted) run (assert the replacement run's formatting matches, proving the `rPr` copy actually happens); a match spanning a `w:tab` (assert the `w:tab` element is fully removed, no orphaned empty element); replacement text longer than the match; replacement text shorter than the match; pure deletion (`replacement_text=""`, assert no stray empty run is left behind); a match at the paragraph's absolute start and, separately, its absolute end; an entire paragraph's text replaced with `""` (paragraph ends up with zero runs, document stays valid and readable).
- **Functional, location mode, synthetic documents:** a match spanning three runs (leftmost partial, middle fully consumed and removed, rightmost partial - the general "sandwich" case, chosen specifically to catch a replacement-placement regression: the new run must land *between* the kept prefix and the kept suffix, not after both); the same fully-consumed-middle-run case with only a prefix kept (no suffix); a prefix-empty match on a paragraph other than the first, to confirm the placement rule isn't accidentally position-dependent.
- **Functional, global mode:** replaces all 4 occurrences of a search term across 2 paragraphs in `run_split.docx`, with the exact expected `replacements_made`; a paragraph with 3 occurrences of the same text is replaced correctly with no offset drift; case-insensitive global replace across four different casings of the same word; `replacement_text` that itself contains `search_text` (e.g. `"cat"` → `"cats"`) replaces exactly the original occurrence count once each, never re-matching the freshly-inserted text; the same self-referential case across multiple paragraphs, confirming no cross-paragraph drift either.
- **Formatting-fidelity:** every paragraph not containing a match is byte-identical (serialized XML) before and after; every non-`word/document.xml` zip part is byte-identical (content and `ZipInfo` metadata) before and after; the replacement run's `w:rPr` is an independent deep copy, never the same object as the source run's (mutating one afterward cannot affect the other).
- **Atomicity:** a global replace where one of several matches spans a run-container boundary writes nothing at all to disk - not even the other, otherwise-valid matches - proving the "abort the whole call" claim in [Error Behavior](#7-error-behavior), not just that an error is raised.
- **Run-container boundaries:** a match fully inside one `w:hyperlink` spanning two runs is allowed; a match fully inside one `w:ins` block is allowed; a match starting inside a `w:hyperlink`/`w:ins` and continuing into plain text outside it is rejected; a match spanning two distinct `w:ins` elements (same tag, different identity) is rejected.
- **Unicode/overlap edge cases:** non-overlapping-match semantics under replace (mirrors `find_text`'s); a length-changing case fold (Turkish dotted capital İ) earlier in a paragraph does not desynchronize a later match's offsets; an astral character (outside the Basic Multilingual Plane) in both `search_text` and `replacement_text`.
- **Sequential edits:** three successive `replace_text_in_document` calls against the same file, each re-opening and re-writing it, all apply correctly and leave a document every later call and every read tool can still parse.
- **Footnote survival:** editing text immediately before a footnote reference (`tests/fixtures/minimal.docx`) and, separately, text immediately after one (a synthetic document, since `minimal.docx`'s anchor has no trailing text) both leave the reference untouched; re-running `get_document_footnotes` against the edited file resolves the anchor identically to before the edit.
- **Error/edge:** out-of-range `paragraph_index` (including negative); out-of-range offsets (including `start_offset >= end_offset`); stale location (obtained, then invalidated by an intervening replace, then reused; separately confirmed to honor `case_sensitive` in both directions); zero matches in global mode; empty `search_text`; a synthetic run-container-boundary-spanning match (rejected, nothing written); simulated crash mid-write (original file byte-for-byte intact, proven both at the shared `atomic_write_part` level and directly at the `replace_text_in_document` level); missing file; non-`.docx`/corrupt-ZIP input; missing `word/document.xml`; malformed `word/document.xml`; missing `<w:body>`; oversized file (plus a file at exactly the size limit, accepted); XXE-crafted `.docx` (entity never resolved; the edit still succeeds and no secret content leaks into the written bytes).
