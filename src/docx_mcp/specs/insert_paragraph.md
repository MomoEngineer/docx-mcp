## 1. Purpose

Insert a new paragraph — body text, or a heading at an explicit level — at a given position in a `.docx` file's body, without disturbing any existing paragraph's text or formatting. A plain body-text insertion (no `heading_level` given) inherits the local formatting (`w:pPr`: style, indentation, spacing, list membership) of the paragraph it is inserted next to, so it visually blends into its surroundings rather than merely sharing a style name — except a section-boundary marker (`w:sectPr`), which is never inherited (see [Formatting & Safety Guarantees](#6-formatting--safety-guarantees)).

## 2. Input Schema

| Parameter | Type | Required | Description / Value range |
| --- | --- | --- | --- |
| `path` | `str` | yes | Filesystem path to a `.docx` file. Same resolution and sandboxing rules as `read_document` (see [specs/read_document.md §2](read_document.md#2-input-schema)). |
| `text` | `str` | yes | The new paragraph's plain text content. May be the empty string (a valid, empty paragraph with no runs). Plain content only — no heading `"# "` prefix or footnote `"[^N]"` marker syntax; use `heading_level` to make the paragraph a heading, and `add_footnote` (Phase 6) to attach a footnote to it afterward. |
| `after_paragraph_index` | `int \| null` | no, default `null` | 0-based index, among the document's **current** top-level `w:body/w:p` paragraphs (identical population/indexing to `get_structure`'s `paragraphs`, `find_text`'s/`replace_text`'s `location.paragraph_index`), of the paragraph the new one is inserted **immediately after**. `null` (default) inserts the new paragraph at the very start of the body, before the current paragraph 0 (or, if the document currently has zero paragraphs, as its only paragraph). To append at the end of the document, pass the index of the current *last* paragraph (e.g. `get_structure`'s `paragraphs[-1].paragraph_index`, or `len(paragraphs) - 1`) — there is no separate "append" mode or sentinel; this is the one, unambiguous way both "insert after paragraph N" and "append at the end" are expressed. |
| `heading_level` | `int \| null` | no, default `null` | `1`–`9`. Given, the new paragraph becomes a heading at that level (Word's built-in `HeadingN` style), independent of the paragraph it is inserted next to. `null` (default): the new paragraph is plain body text — see [Formatting & Safety Guarantees](#6-formatting--safety-guarantees) for exactly how its style is derived from context. |

JSON Schema, as generated by the MCP SDK from the function signature:

```json
    "heading_level": { "anyOf": [{ "type": "integer" }, { "type": "null" }], "default": null }

```

## 3. Output Schema

Sketch:

```json
{ "paragraph_index": 3 }
```

JSON Schema, generated by the MCP SDK from the `InsertParagraphResult` model:

```json
{
  "type": "object",
  "properties": {
    "paragraph_index": { "type": "integer" }
  },
  "required": ["paragraph_index"]
}
```

- **`paragraph_index`** — the 0-based index the newly inserted paragraph now occupies among the document's top-level paragraphs (`0` if `after_paragraph_index` was `null`, otherwise `after_paragraph_index + 1`). Unlike `replace_text`'s deliberate omission of a post-edit location, returning this is safe and useful here: it is a plain structural position freshly computed against the document this same call just wrote, not a piece of content that could itself be stale — a caller can pass it straight into a following `delete_paragraph` or use it to reason about further inserts, exactly as any other tool's `paragraph_index` output is already used elsewhere in this project.

## 4. Assumptions and Preconditions

- Same as [specs/replace_text.md §4](replace_text.md#4-assumptions-and-preconditions): `path` resolves inside an allowed root, checked before the file is opened; the file is a valid ZIP containing at least `word/document.xml`; the write path re-serializes and rewrites `word/document.xml` the same way.

## 5. Limitations (Non-Goals)

- **Top-level body paragraphs only.** Identical scope to every other tool in this project: `after_paragraph_index` addresses `w:body/w:p` direct children only, never a paragraph inside a table cell (`w:tbl`/`w:tc`), which has no such index.
- **A Word table-of-contents field is not recomputed.** If the new paragraph is a heading, Word's TOC field (if the document has one) will not reflect it until the field is refreshed inside Word itself — a boundary documented in [Roadmap.md, Phase 5](../../../Roadmap.md#phase-5--paragraph-level-structure-edits-insert_paragraph-delete_paragraph), not a bug in this tool.
- **Style inheritance is paragraph-level only, not character-level.** The new paragraph's text is inserted as a single run with no `w:rPr` (no explicit bold/italic/font/etc.), regardless of the anchor paragraph's run formatting — see [ADR-0006 §Decision.3](../../../docs/adr/0006-phase-5-paragraph-edit-module-layout.md) for why "style" here means `w:pPr`, the same granularity `get_structure`'s `style_id` already uses, not run-level character formatting.
- **Heading detection for the inheritance rule uses the built-in `HeadingN`-id heuristic only** (`document.py`'s `heading_level_from_style_prefix`), the same one `read_document` already uses — **not** `get_structure`'s fuller `styles.xml`/`basedOn`-chain resolution. A custom-named style that only resolves to a heading level through that chain (e.g. `tests/fixtures/structured.docx`'s `MySectionHeading`) is treated as an ordinary body paragraph by this tool: inserting plain body text after it copies its `w:pPr` verbatim, exactly as for any other non-heading anchor, rather than being recognized as "already a heading" and getting no `w:pPr`. See [ADR-0006 §Decision.4](../../../docs/adr/0006-phase-5-paragraph-edit-module-layout.md) for the rationale (keeps this write tool from needing to open `word/styles.xml` at all).
- **No numbering restart/insertion logic.** If the anchor paragraph is a numbered-list item, a plain body-text insertion after it inherits the same `w:numPr` (list/level) as a natural consequence of copying `w:pPr` verbatim — this tool does not compute or adjust list numbering itself (Word does that at render time, as for any other list edit); it also does not offer a way to *start* a new list.
- **`heading_level` must be `1`–`9`.** Any other integer is rejected (see [Error Behavior](#7-error-behavior)); there is no way to request an arbitrary custom paragraph style (see [ADR-0006 Alternatives](../../../docs/adr/0006-phase-5-paragraph-edit-module-layout.md) for why a raw style-id parameter was rejected).

## 6. Formatting & Safety Guarantees

- **Atomic write:** identical to `replace_text` — see [specs/replace_text.md §6](replace_text.md#6-formatting--safety-guarantees). Only `word/document.xml` is rewritten.
- **Untouched paragraphs and zip parts are unchanged:** every existing paragraph's XML, and every zip part other than `word/document.xml`, is byte-identical before and after.
- **Style-inheritance rule** (see [ADR-0006 §Decision.3–4](../../../docs/adr/0006-phase-5-paragraph-edit-module-layout.md) for the full rationale), applied to the **anchor paragraph** — the paragraph named by `after_paragraph_index`, or the current paragraph 0 when `after_paragraph_index` is `null` and at least one paragraph exists, or no anchor at all when the document currently has zero paragraphs:
  1. `heading_level` given → the new paragraph's `w:pPr` is built fresh, containing only `<w:pStyle w:val="HeadingN"/>` — the anchor's own formatting is irrelevant.
  2. `heading_level` omitted, and the anchor exists and is **not** recognized as a heading (see [Limitations](#5-limitations-non-goals)) → the anchor's entire `w:pPr` element is deep-copied onto the new paragraph verbatim, **except** any `w:sectPr` child, which is always stripped (see below) — or no `w:pPr` at all if the anchor has none, or if stripping `w:sectPr` leaves nothing else behind.
  3. `heading_level` omitted, and the anchor either does not exist (empty document) or **is** recognized as a heading → the new paragraph gets no `w:pPr` at all (the document's implicit default paragraph style), specifically so a plain body-text insertion right after a heading does not silently become another heading.
- **A `w:sectPr` is never copied onto the new paragraph.** If the anchor paragraph's `w:pPr` contains a `w:sectPr` (marking it as the last paragraph of a document section), that element is stripped from the copy before it is attached to the new paragraph — copying it verbatim would duplicate the anchor's section properties (page size, margins, header/footer references, ...) and silently create an unintended extra section break. See [ADR-0006 §Decision.8](../../../docs/adr/0006-phase-5-paragraph-edit-module-layout.md); the anchor itself keeps its own `w:sectPr` untouched.
- **Insertion position in the XML tree:** the new `w:p` is inserted as an XML sibling immediately after the anchor (`after_paragraph_index` given), or immediately before the current first paragraph (`after_paragraph_index` is `null`, at least one paragraph exists), or immediately before `w:body`'s own direct `w:sectPr` child if present, else appended as `w:body`'s last child (`after_paragraph_index` is `null`, zero paragraphs exist) — the last case guards against inserting after a body-level section-properties element, which must remain the body's final child.
- Path resolution, sandboxing, and hardened XML parsing are identical to every other tool.

## 7. Error Behavior

| Case | Behavior |
| --- | --- |
| `path` escapes all allowed roots / no allowed roots configured / UNC network path | Identical to `read_document`, checked before any write attempt. |
| File does not exist, is not a file, is not a valid ZIP, exceeds the size limit, or is missing/malformed `word/document.xml` | Identical to `read_document` — checked before any write attempt. |
| `after_paragraph_index` is given and is negative, or `>=` the document's current top-level paragraph count | Clear "after_paragraph_index references a paragraph that does not exist" error. Nothing is written. |
| `heading_level` is given and is not an integer in `1..9` | Clear "heading_level must be between 1 and 9" error. Nothing is written. |
| The process is interrupted/crashes after the new `word/document.xml` content is computed but before the atomic replace completes | The original file is untouched — verified by a dedicated simulated-crash test. |

## 8. Test Coverage

Reference: `tests/test_paragraph_edit.py` (functional, formatting-fidelity, and error/edge at the `insert_paragraph_in_document` level), `tests/test_insert_paragraph_tool.py` (contract, functional, error/edge at the MCP-protocol level), `tests/test_security.py` (path sandboxing, shared), `tests/integration/test_paragraph_edit_consistency.py` (an inserted paragraph is visible, with the correct text and position, to `read_document`/`get_structure`/`find_text` afterward), `tests/integration/test_paragraph_edit_python_docx_roundtrip.py` (independent-library re-verification: the edited document reopens correctly in `python-docx`, and its object model agrees on style names and inherited formatting).

- **Contract:** tool discoverable via `list_tools`; name, description, input schema (including the optional, nullable `after_paragraph_index`/`heading_level`), output schema, and version (`_meta`) match this spec.
- **Functional, against `tests/fixtures/paragraph_edits.docx`:** insert plain body text after a heading (must **not** become a heading — no `w:pPr` at all); insert plain body text after a body paragraph with non-trivial local formatting (indentation/alignment; new paragraph's `w:pPr` matches byte-for-byte); insert at the end of the document (after the current last paragraph); insert at the very start (`after_paragraph_index=null`, non-empty document); insert into a completely empty document (`after_paragraph_index=null`, zero paragraphs, no `w:pPr` on the result); insert a heading at each of levels 1–9 after a plain body paragraph (`w:pPr` is exactly `<w:pStyle w:val="HeadingN"/>`, none of the anchor's own formatting carried over); insert an empty-string paragraph (zero runs, valid document afterward); insert text after a numbered-list-item anchor (new paragraph's `w:numPr` matches the anchor's).
- **Formatting-fidelity:** every paragraph other than the newly inserted one is byte-identical (serialized XML) before and after; every non-`word/document.xml` zip part is byte-identical (content and `ZipInfo` metadata) before and after; the new paragraph's copied `w:pPr` (inheritance case) is an independent deep copy, never the same object as the anchor's (mutating one afterward cannot affect the other).
- **Anchor-is-a-heading exception:** inserting plain body text (no `heading_level`) after a `Heading1`/`Heading2` paragraph produces a paragraph with no `w:pPr`, not a copy of the heading's `w:pStyle` — the specific bug class [ADR-0006](../../../docs/adr/0006-phase-5-paragraph-edit-module-layout.md) reasons through explicitly.
- **Anchor-carries-a-`w:sectPr` exception:** inserting plain body text after a synthetic paragraph whose `w:pPr` holds both other formatting (e.g. `w:jc`) and a `w:sectPr` copies only the other formatting, never the `w:sectPr`; a second synthetic case whose `w:pPr` holds *only* a `w:sectPr` produces a new paragraph with no `w:pPr` at all; in both cases the anchor's own `w:sectPr` remains present and untouched afterward. The bug this regression-tests (found during a post-implementation verification pass, [ADR-0006 §Decision.8](../../../docs/adr/0006-phase-5-paragraph-edit-module-layout.md)): duplicating section properties onto the new paragraph.
- **Custom-style boundary:** inserting plain body text after `structured.docx`'s `MySectionHeading` paragraph (a heading only via its `styles.xml` `basedOn` chain) copies its `w:pPr` verbatim, confirming this tool does **not** open `styles.xml` and therefore does not recognize it as a heading.
- **Error/edge:** `after_paragraph_index` negative; `after_paragraph_index` equal to and greater than the paragraph count; `heading_level` of `0`, `10`, and `-1`; simulated crash mid-write (original file byte-for-byte intact); missing file; non-`.docx`/corrupt-ZIP input; missing `word/document.xml`; malformed `word/document.xml`; missing `<w:body>`; oversized file (plus a file at exactly the size limit, accepted); XXE-crafted `.docx` (entity never resolved; the insert still succeeds).
- **Round-trip:** the returned `paragraph_index`, passed to a following `get_structure`/`read_document`/`find_text` call, addresses exactly the newly inserted paragraph.
