# Tool Specification: `delete_paragraph`

> Written before the implementation, per [CONTRIBUTING.md §4](../../../CONTRIBUTING.md#4-workflow-spec--tests--docs--implementation).

---

## Metadata

| Field | Value |
| --- | --- |
| **Tool name** | `delete_paragraph` |
| **Version** | `1.0.0` |
| **Type** | Write |
| **Status** | Implemented |

---

## 1. Purpose

Remove a whole paragraph from a `.docx` file's body by its `paragraph_index`, without disturbing any other paragraph's text or formatting and without corrupting the document's required structure (see [Limitations](#5-limitations-non-goals) for the one case this tool refuses rather than silently breaking). An optional `expected_text` guards against acting on a stale index left over from an earlier read.

## 2. Input Schema

| Parameter | Type | Required | Description / Value range |
| --- | --- | --- | --- |
| `path` | `str` | yes | Filesystem path to a `.docx` file. Same resolution and sandboxing rules as `read_document` (see [specs/read_document.md §2](read_document.md#2-input-schema)). |
| `paragraph_index` | `int` | yes | 0-based index, among the document's **current** top-level `w:body/w:p` paragraphs, of the paragraph to remove — identical population/indexing to `get_structure`'s `paragraphs`, `find_text`'s/`replace_text`'s `location.paragraph_index`, and `insert_paragraph`'s returned `paragraph_index`. |
| `expected_text` | `str \| null` | no, default `null` | If given, must equal the target paragraph's current plain text (`get_structure`'s `paragraphs[i].text`-equivalent — no heading `"# "` prefix, no footnote `"[^N]"` marker) exactly, or the call fails instead of deleting — the same staleness check `replace_text`'s `location`/`search_text` pair already performs, applied to whole-paragraph deletion. `null` (default) skips the check. |

JSON Schema, as generated by the MCP SDK from the function signature:

```json
{
  "type": "object",
  "properties": {
    "path": { "type": "string" },
    "paragraph_index": { "type": "integer" },
    "expected_text": { "anyOf": [{ "type": "string" }, { "type": "null" }], "default": null }
  },
  "required": ["path", "paragraph_index"]
}
```

## 3. Output Schema

Sketch:

```json
{ "deleted_text": "This paragraph is gone now." }
```

JSON Schema, generated by the MCP SDK from the `DeleteParagraphResult` model:

```json
{
  "type": "object",
  "properties": {
    "deleted_text": { "type": "string" }
  },
  "required": ["deleted_text"]
}
```

- **`deleted_text`** — the plain text (same rendering as `get_structure`'s `paragraphs[i].text`) the removed paragraph held immediately before deletion. Always returned, even when `expected_text` was also given (in which case it is always identical to `expected_text`) — a caller that skipped the staleness check still gets a receipt of exactly what was removed, directly informed by this project's principle that a destructive operation should not leave the caller guessing what happened.

## 4. Assumptions and Preconditions

- Same as [specs/replace_text.md §4](replace_text.md#4-assumptions-and-preconditions): `path` resolves inside an allowed root, checked before the file is opened; the file is a valid ZIP containing at least `word/document.xml`; the write path re-serializes and rewrites `word/document.xml` the same way.

## 5. Limitations (Non-Goals)

- **Top-level body paragraphs only** — same scope as `insert_paragraph`; a `paragraph_index` addressing a table cell is not meaningful because no such index exists.
- **A Word table-of-contents field is not recomputed.** Deleting a heading paragraph does not update Word's TOC field (if present) until it is refreshed inside Word itself — the same documented boundary as `insert_paragraph` (see [Roadmap.md, Phase 5](../../../Roadmap.md#phase-5--paragraph-level-structure-edits-insert_paragraph-delete_paragraph)).
- **A footnote reference inside the deleted paragraph is not specially cleaned up.** The `w:footnoteReference` is removed along with the rest of the paragraph, but the corresponding `<w:footnote>` entry in `word/footnotes.xml` is deliberately left in place, now unreferenced — consistent with [specs/get_footnotes.md §5](get_footnotes.md#5-limitations-non-goals)'s existing "an orphaned, never-referenced footnote is intentionally excluded" behavior. Word renders remaining footnotes' numbering from reference order, so this causes no visible gap or corruption; actively removing the now-unused `<w:footnote>` entry was deferred, pending real footnote-editing infrastructure (see [ADR-0006 §Decision.5](../../../docs/adr/0006-phase-5-paragraph-edit-module-layout.md)) — Phase 6 has since shipped (`add_footnote`/`edit_footnote`, [ADR-0007](../../../docs/adr/0007-phase-6-footnote-edit-module-layout-and-multi-part-atomic-write.md)) without taking on this cleanup, so it remains a deliberately deferred, unscheduled possible future enhancement rather than a near-term plan (see [docs/adr/README.md §5](../../../docs/adr/README.md#5-openplanned-adrs)).
- **A paragraph carrying the document's section properties cannot be deleted** — see [Error Behavior](#7-error-behavior). This is a refusal, not a silent workaround; a caller that genuinely needs to restructure sections has no tool for that in this project yet.
- **No undo.** Unlike `replace_text` (which can be "undone" by another `replace_text` call restoring the original text), a deleted paragraph's exact original XML — formatting nuances included — cannot be reconstructed from `insert_paragraph` alone. `expected_text` mitigates acting on a *stale index*, not the irreversibility of a correctly-targeted deletion.

## 6. Formatting & Safety Guarantees

- **Atomic write:** identical to `replace_text` — see [specs/replace_text.md §6](replace_text.md#6-formatting--safety-guarantees). Only `word/document.xml` is rewritten.
- **Untouched paragraphs and zip parts are unchanged:** every paragraph other than the deleted one, and every zip part other than `word/document.xml`, is byte-identical before and after.
- **The `w:p` element is removed as a whole**, as a single XML-tree operation on `word/document.xml`'s `<w:body>` — no orphaned sibling elements, no dangling text.
- Path resolution, sandboxing, and hardened XML parsing are identical to every other tool.

## 7. Error Behavior

| Case | Behavior |
| --- | --- |
| `path` escapes all allowed roots / no allowed roots configured / UNC network path | Identical to `read_document`, checked before any write attempt. |
| File does not exist, is not a file, is not a valid ZIP, exceeds the size limit, or is missing/malformed `word/document.xml` | Identical to `read_document` — checked before any write attempt. |
| `paragraph_index` is negative, or `>=` the document's current top-level paragraph count | Clear "paragraph_index references a paragraph that does not exist" error. Nothing is written. |
| `expected_text` is given and does not equal the target paragraph's current plain text | Clear "stale paragraph_index" error — the document has changed since the caller last read this index (e.g. an intervening insert/delete), or the index never pointed at this text. Nothing is written. |
| The target paragraph's `w:pPr` contains a `w:sectPr` | Clear error naming the section-properties conflict (see [Limitations](#5-limitations-non-goals)); nothing is written. |
| The process is interrupted/crashes after the new `word/document.xml` content is computed but before the atomic replace completes | The original file is untouched — verified by a dedicated simulated-crash test. |

## 8. Test Coverage

Reference: `tests/test_paragraph_edit.py` (functional, formatting-fidelity, and error/edge at the `delete_paragraph_from_document` level), `tests/test_delete_paragraph_tool.py` (contract, functional, error/edge at the MCP-protocol level), `tests/test_security.py` (path sandboxing, shared), `tests/integration/test_paragraph_edit_consistency.py` (a deleted paragraph disappears from `read_document`/`get_structure`, and a footnote it anchored disappears from `get_footnotes`' output while the corresponding `word/footnotes.xml` entry survives, unreferenced), `tests/integration/test_paragraph_edit_python_docx_roundtrip.py` (independent-library re-verification: repeated deletions still leave a document `python-docx` can reopen correctly).

- **Contract:** tool discoverable via `list_tools`; name, description, input schema (including the optional, nullable `expected_text`), output schema, and version (`_meta`) match this spec.
- **Functional, against `tests/fixtures/paragraph_edits.docx`:** delete a body paragraph in the middle of the document (surrounding paragraphs' indices shift down by one, correctly re-addressable afterward); delete the first paragraph; delete the last paragraph (not the one carrying the body's section properties); delete a heading paragraph; `deleted_text` matches the paragraph's actual prior content exactly, including for a heading (marker-free, per `get_structure`'s rendering, not `read_document`'s `"# "`-prefixed one); `expected_text` given and matching succeeds; `expected_text` omitted succeeds unconditionally.
- **Formatting-fidelity:** every paragraph other than the deleted one is byte-identical (serialized XML) before and after; every non-`word/document.xml` zip part is byte-identical (content and `ZipInfo` metadata) before and after.
- **Footnote survival:** deleting a paragraph anchoring a footnote (`tests/fixtures/footnotes.docx`) removes it from `get_footnotes`' output while a *different* paragraph's footnote in the same document remains correctly resolved; the now-orphaned `<w:footnote>` entry is still present, byte-identical, in `word/footnotes.xml` afterward.
- **Section-properties guard:** deleting a synthetic paragraph whose `w:pPr` contains a `w:sectPr` is rejected with a clear error, and nothing is written, **even when a correctly-matching `expected_text` is also given** (the guard is not bypassable via the staleness check); deleting an ordinary paragraph in the same document (not the one carrying `w:sectPr`) still succeeds.
- **Error/edge:** `paragraph_index` negative; `paragraph_index` equal to and greater than the paragraph count; `expected_text` not matching (stale-index rejection); `expected_text` matching only case-differently is still rejected (exact-match only, no `case_sensitive` option); simulated crash mid-write (original file byte-for-byte intact); missing file; non-`.docx`/corrupt-ZIP input; missing `word/document.xml`; malformed `word/document.xml`; missing `<w:body>`; oversized file (plus a file at exactly the size limit, accepted); XXE-crafted `.docx` (entity never resolved; the delete still succeeds).
- **Sequential edits:** an `insert_paragraph` immediately followed by a `delete_paragraph` of the very paragraph it just inserted (via the returned `paragraph_index`) leaves the document in its original state.

## 9. Examples

Against `tests/fixtures/paragraph_edits.docx`, removing paragraph 3 ("Second body paragraph."), with the staleness guard engaged:

Request:

```json
{
  "path": "/workspace/reports/paragraph_edits.docx",
  "paragraph_index": 3,
  "expected_text": "Second body paragraph."
}
```

Response:

```json
{ "deleted_text": "Second body paragraph." }
```

Had the document changed since the caller last read paragraph 3 (e.g. an earlier `insert_paragraph`/`delete_paragraph` call shifted indices), a mismatching `expected_text` would fail the call with a clear "stale paragraph_index" error instead of deleting the wrong paragraph; omitting `expected_text` skips that check and deletes unconditionally.
