## 1. Purpose

Return a `.docx` file's structural outline — an indexed list of top-level paragraphs with their resolved heading level, a derived table of contents, every table rendered as rows of cell text, and a lightweight footnote-anchor index — so a calling agent can navigate and reason about a document's shape without re-parsing `read_document`'s flattened text or resolving heading styles itself.

## 3. Output Schema

Sketch:

```json
{
  "paragraphs": [
    { "paragraph_index": 0, "text": "Introduction", "style_id": "Heading1", "heading_level": 1 }
  ],
  "toc": [
    { "paragraph_index": 0, "level": 1, "text": "Introduction" }
  ],
  "tables": [
    { "table_index": 0, "rows": [["Header A", "Header B"], ["Value 1", "Value 2"]] }
  ],
  "footnotes": [
    { "id": "1", "paragraph_index": 2 }
  ]
}
```

JSON Schema, generated by the MCP SDK from the `GetStructureResult` model (Pydantic v2 nests each list-item model under `$defs` and references it via `$ref` — the contract test checks the properties below, field types, and required-ness, not byte-exact equality with a hand-written schema, consistent with [specs/read_document.md §2](read_document.md#2-input-schema)):

```json
          "paragraph_index": { "type": "integer" },

      "items": {

  "required": ["paragraphs", "toc", "tables", "footnotes"]

```

Field semantics:

- **`paragraphs`** — every direct `w:body/w:p` child (the same population `read_document` walks; paragraphs nested inside table cells are *not* included here — see [Limitations](#5-limitations-non-goals)), in document order, 0-indexed by `paragraph_index`.
  - `text` is **plain**: no `"# "` heading prefix and no inline `"[^N]"` footnote marker (those are `read_document`'s rendering convention, not structural data). Multiple runs within a paragraph are concatenated exactly as `read_document` does (`w:t`, `w:tab` → literal tab); `w:delText` excluded, `w:ins`-wrapped `w:t` included — identical text-assembly rules to [specs/read_document.md §3](read_document.md#3-output-schema), just without the markers.
  - `style_id` is the raw `w:pPr/w:pStyle/@w:val`, or `null` if the paragraph has no style reference.
  - `heading_level` is the *resolved* heading level (1–9), or `null` if the paragraph is not a heading. Resolution order (first applicable rule wins — direct/local formatting overrides style-derived formatting, per OOXML's own precedence rule):
    1. **If the paragraph itself carries a `w:pPr/w:outlineLvl` element with a valid value** (an integer `0`–`9`), that element is authoritative and no further step is consulted — this is a terminal decision, not merely a first guess. Values `0`–`8` map to levels `1`–`9`; value `9` means **"Body Text"** — OOXML's explicit way to mark a paragraph as deliberately outside the outline — and resolves to `heading_level: null`, not level 10 and not a fallthrough to steps 2–4. (Concretely: a paragraph styled `Heading1` that *also* carries a direct `w:outlineLvl w:val="9"` override is **not** a heading — the direct override wins.) A `w:outlineLvl` element whose value is missing, non-numeric, or outside `0`–`9` (a malformed or adversarial `.docx`, never produced by Word itself) is treated as if the element were absent — it is **not** authoritative and does **not** produce an out-of-range `heading_level` (e.g. `0` from `val="-1"`, or `101` from `val="100"`); resolution falls through to step 2.
    2. **Otherwise** (no direct `w:outlineLvl` element present, or its value was malformed/out-of-range per step 1), the paragraph's referenced style (`w:pPr/w:pStyle/@w:val`) is looked up in `word/styles.xml`, and its own `w:pPr/w:outlineLvl` is used if it carries a valid `0`–`9` value (same 0–8→1–9 / 9→`null` mapping); if not — absent, or itself malformed/out-of-range — the style's `w:basedOn` chain is walked (nearest ancestor first) until one declares a validly-valued `outlineLvl`, up to 64 hops (guards against a malformed circular `w:basedOn` chain — see [Error Behavior](#7-error-behavior)).
    3. **Otherwise** (no valid `outlineLvl` found anywhere in the style chain, or the style id isn't found in `styles.xml` at all), if the style id starts with `"Heading"` followed only by digits (Word's built-in Heading 1–9 styles, the same heuristic [specs/read_document.md §5](read_document.md#5-limitations-non-goals) documents), that digit suffix is used directly — the Phase 1 behavior, kept as a fallback for a `styles.xml` that is missing, doesn't define the built-in Heading styles explicitly, or is absent entirely.
    4. **Otherwise**, `null` (not a heading).
- **`toc`** — every entry of `paragraphs` whose `heading_level` is not `null`, filtered and re-expressed as `{paragraph_index, level, text}`, in document order. This *is* the document's table of contents as derived from its actual heading structure (not Word's own cached TOC *field*, if one happens to exist in the document — that field's cached display text already surfaces as ordinary body text via `read_document`, per [specs/read_document.md](read_document.md#3-output-schema)'s field-instruction handling).
- **`tables`** — every direct `w:body/w:tbl` child, in document order, 0-indexed by `table_index`, independent of `paragraph_index` (tables and paragraphs are addressed by separate, type-local 0-based sequences — see [Limitations](#5-limitations-non-goals)).
  - `rows` is one entry per `w:tr`, each a list of one string per `w:tc` in that row, in document order.
  - A cell's text is the concatenation of its contained paragraphs' `read_document`-style rendering (heading markers and inline footnote markers included, exactly like a body paragraph — a cell *can* validly contain a heading-styled or footnote-anchored paragraph), multiple paragraphs within one cell joined by `"\n"`.
  - **Row lengths are not padded to a uniform column count.** A horizontally merged cell (`w:gridSpan`) is a single `w:tc` in the XML, so that row simply has fewer entries than an unmerged row — callers must not assume every row in `rows` has the same length. A vertically merged continuation cell (`w:vMerge` without an explicit master text) keeps its column position but renders as `""` — its content is not duplicated down from the master cell.
- **`footnotes`** — every `w:footnoteReference` found while walking `paragraphs` (so, like `paragraphs`, this does not see footnote references inside a table cell — see [Limitations](#5-limitations-non-goals)), in document order, as `{id, paragraph_index}` of its anchor. This is an **index only** — `id` resolves to content only via `get_footnotes` (Phase 3); `get_structure` never opens `word/footnotes.xml`.

## 4. Assumptions and Preconditions

- Same as [specs/read_document.md §4](read_document.md#4-assumptions-and-preconditions): `path` resolves inside an allowed root, checked before the file is opened; the file is a valid ZIP containing at least `word/document.xml`.
- `word/styles.xml` is **not required** to exist. If missing, or if a referenced style id is not found in it, heading resolution falls through to step 3/4 above rather than failing the whole call — a `.docx` that would satisfy `read_document` must also satisfy `get_structure`.

## 5. Limitations (Non-Goals)

- **`heading_level` here can legitimately disagree with `read_document`'s `"# "` markers for the same paragraph.** `read_document` only recognizes the built-in `HeadingN` style-id prefix (see [specs/read_document.md §5](read_document.md#5-limitations-non-goals)); `get_structure` additionally resolves custom-named heading styles via `styles.xml`. A paragraph styled with a custom style based on `Heading2` is plain, unprefixed text from `read_document` but `heading_level: 2` here — this is intentional (it is exactly the improvement Phase 2 adds), not a consistency bug between the two tools, but a caller combining both outputs must not assume they agree on which paragraphs are headings.
- **`paragraph_index` addresses only top-level body paragraphs** (direct `w:body/w:p` children, the same population `read_document` walks). Text inside a table cell is available via `tables[].rows`, not via `paragraph_index`; a footnote reference inside a table cell is likewise not represented in the `footnotes` index. This mirrors [specs/read_document.md §5](read_document.md#5-limitations-non-goals)'s existing "table content is not extracted" boundary rather than silently extending it — a future phase that needs table-cell paragraphs individually addressable is a deliberate, separate scope decision, not assumed here.
- **Nested tables are not extracted.** Only direct `w:body/w:tbl` elements are walked; a `w:tbl` nested inside a `w:tc` is not represented anywhere in `tables`, and its text is not included in the containing cell's text either.
- **`table_index` and `paragraph_index` are independent sequences**, not a single interleaved "document position." A table's position relative to its surrounding paragraphs cannot be recovered from this output.
- **Word's own cached TOC *field*, if the document has one, is not specially recognized here.** `toc` is always derived from resolved heading levels; a document's actual `w:sdt`/`fldSimple` table-of-contents field content already appears as ordinary text via `read_document` (ADR: none needed, this is existing Phase 1 behavior, restated here for clarity).
- **List numbering is not computed** — same as [specs/read_document.md §5](read_document.md#5-limitations-non-goals).
- **Row-length raggedness from merged cells is not normalized** — see [Output Schema](#3-output-schema); a caller that needs a rectangular grid must pad/interpret `w:gridSpan`/`w:vMerge` semantics itself.

## 6. Formatting & Safety Guarantees

- Read-only, same as `read_document` — never opens the target file for writing.
- `path` is resolved and validated against the allow-listed roots, and a UNC network path rejected, before the file is opened — identical to [specs/read_document.md §6](read_document.md#6-formatting--safety-guarantees).
- Every internal XML part this tool reads — `word/document.xml` **and now also `word/styles.xml`** — is parsed with the same hardened `lxml` parser (`resolve_entities=False`, `no_network=True`) as `read_document`, so a crafted external entity in either part cannot read local files or trigger network access (see [ADR-0001](../../../docs/adr/0001-ooxml-library-and-module-layout.md), [ADR-0003](../../../docs/adr/0003-phase-2-module-layout.md)).

## 7. Error Behavior

| Case | Behavior |
| --- | --- |
| `path` escapes all allowed roots / no allowed roots configured / UNC network path | Identical to `read_document` (see [specs/read_document.md §7](read_document.md#7-error-behavior)). |
| File does not exist, is not a file, is not a valid ZIP, exceeds the size limit, or is missing/malformed `word/document.xml` | Identical to `read_document` — these checks are shared, unchanged logic (see [ADR-0003](../../../docs/adr/0003-phase-2-module-layout.md)). |
| `word/styles.xml` is missing | Not an error — heading resolution falls through to the digit-suffix heuristic (step 3) for every paragraph, exactly as `read_document` already behaves. |
| `word/styles.xml` is present but malformed XML | Rejected with a clear "not a valid .docx file: malformed XML in word/styles.xml" error — a `.docx` that declares the part but corrupts it is treated as invalid, the same posture as a malformed `word/document.xml`. |
| A style's `w:basedOn` chain exceeds 64 hops (malformed circular reference) | Not an error — that style's outline-level resolution stops (falls through to step 3/4) instead of looping or raising, since the *document* is still readable even if one style definition is circular. |
| `word/styles.xml` contains a DTD declaring an external entity | Parsed successfully; the entity reference is never resolved (same guarantee as `word/document.xml`, see [specs/read_document.md §7](read_document.md#7-error-behavior)). |

## 8. Test Coverage

Reference: `tests/test_structure.py` (functional and error/edge at the `get_document_structure` level, including heading resolution and XXE hardening for `styles.xml`), `tests/test_get_structure_tool.py` (contract, functional, error/edge at the MCP-protocol level), `tests/test_security.py` (path sandboxing, shared), `tests/integration/test_read_document_and_get_structure_consistency.py` (cross-tool checks, including the documented custom-heading-style divergence from §5).

- **Contract:** tool discoverable via `list_tools`; name, description, input schema, output schema, and version (`_meta`) match this spec.
- **Functional:** against `tests/fixtures/structured.docx` (three heading levels including one custom-named style resolved via `w:basedOn`, a table with a horizontal merge, plain paragraphs) and `tests/fixtures/minimal.docx` (reused for the footnote-anchor-index assertion, since it already carries one footnote reference at a known paragraph).
- **Error/edge:** path outside allowed roots; oversized file rejected before parsing, file at exactly the size limit accepted; missing `word/styles.xml` (falls back cleanly); malformed `word/styles.xml`; circular `w:basedOn` chain (does not hang/crash); a *deep but acyclic* `w:basedOn` chain (5 levels) resolves correctly, proving the 64-hop guard doesn't reject legitimate chains; a table row with a horizontally merged cell (shorter row, asserted explicitly, not treated as a bug); a vertically merged continuation cell (renders as `""`); multiple top-level tables indexed independently of the interleaved paragraphs; a table with zero rows; unicode and astral characters in headings and table cells; `outlineLvl` value `9` ("Body Text") resolves to `heading_level: null`; a paragraph with a `Heading1`-prefixed style that *also* carries a direct `outlineLvl w:val="9"` override resolves to `heading_level: null` (direct formatting wins over style, per step 1's precedence rule); an out-of-range (`-1`, `10`, `100`) or non-numeric (`abc`, empty) direct `outlineLvl` value falls through instead of producing a nonsensical `heading_level`, all the way to the `HeadingN` heuristic when a `pStyle` is present; a style's own malformed `outlineLvl` falls through to its `w:basedOn` ancestor instead of stopping the chain walk; XXE-crafted `styles.xml` (external entity not resolved).
