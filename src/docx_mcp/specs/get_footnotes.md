| Field | Value |

## 1. Purpose

Return every footnote a `.docx` file's body actually references — its ID, the paragraph that anchors it, and its resolved text content — so a calling agent can read footnote content directly instead of only seeing `read_document`'s inline `"[^N]"` markers or `get_structure`'s anchor-only index.

## 2. Input Schema

| Parameter | Type | Required | Description / Value range |
| --- | --- | --- | --- |
| `path` | `str` | yes | Filesystem path to a `.docx` file. Same resolution and sandboxing rules as `read_document` (see [specs/read_document.md §2](read_document.md#2-input-schema)). |

JSON Schema, as actually generated by the MCP SDK from the `path: str` parameter:

```json
{
  "type": "object",
  "properties": {
    "path": { "type": "string" }
  },
  "required": ["path"]
}
```

## 3. Output Schema

Sketch:

```json
{
  "footnotes": [
    { "id": "1", "paragraph_index": 2, "content": "First footnote." },
    { "id": "2", "paragraph_index": 2, "content": "Second footnote." },
    { "id": "3", "paragraph_index": 4, "content": null }
  ]
}
```

JSON Schema, generated by the MCP SDK from the `GetFootnotesResult` model:

```json
{
  "type": "object",
  "properties": {
    "footnotes": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "id": { "type": "string" },
          "paragraph_index": { "type": "integer" },
          "content": { "type": ["string", "null"] }
        },
        "required": ["id", "paragraph_index", "content"]
      }
    }
  },
  "required": ["footnotes"]
}
```

Field semantics:

- **Population is anchor-driven**: `footnotes` has exactly one entry per `w:footnoteReference` found while walking the body's top-level paragraphs (`w:body/w:p`, the same population and traversal `get_structure`'s footnote-anchor index uses — see [ADR-0004](../../../docs/adr/0004-phase-3-footnote-module-and-shared-anchor-resolution.md)), in document order. It is **not** one entry per `w:footnote` declared in `word/footnotes.xml` — see [Limitations](#5-limitations-non-goals) for why, and for what this deliberately excludes.
- **`id`** — the anchor's `w:footnoteReference/@w:id`, as a string (matches `get_structure`'s `footnotes[].id`).
- **`paragraph_index`** — the 0-based index, among top-level body paragraphs, of the paragraph containing the anchor (matches `get_structure`'s `footnotes[].paragraph_index` and the paragraph at which `read_document` places the corresponding `"[^N]"` marker). **Two different footnote ids anchored in the same paragraph produce two separate entries with the same `paragraph_index`** — this is the central case this tool must get right (see [Roadmap.md, Phase 3](../../../Roadmap.md#phase-3--footnotes-read-path-get_footnotes)); the output is a flat list, never a mapping keyed by `paragraph_index`, precisely so this case cannot silently collide two footnotes into one.
- **`content`** — the footnote's text, resolved from `word/footnotes.xml`: the `w:footnote` element whose `@w:id` matches this entry's `id`, its `w:p` children rendered with the same marker-free text assembly `read_document`/`get_structure` use for plain paragraph text (`paragraph_plain_text` — `w:t` and `w:tab`, `w:delText` excluded, `w:ins`-wrapped `w:t` included), multiple paragraphs within one footnote joined by `"\n"`. Deliberately **not** the marker-inclusive rendering `get_structure` uses for table-cell text (`render_paragraph`): a table cell is itself a unit of document structure a caller may navigate into (so its own heading/footnote markers stay meaningful), whereas footnote content is a terminal leaf — text about the document, never itself part of the document's outline or anchor graph — so a heading-style marker leaking into it would be misleading decoration rather than useful structure. `content` is `null` when it cannot be resolved — see [Error Behavior](#7-error-behavior); this is never an error by itself.

## 4. Assumptions and Preconditions

- Same as `read_document`/`get_structure`: `path` resolves inside an allowed root, checked before the file is opened; the file is a valid ZIP containing at least `word/document.xml`.
- `word/footnotes.xml` is **not required** to exist. A document with no footnote anchors in its body normally has no `word/footnotes.xml` part at all; its absence never fails the call (see [Error Behavior](#7-error-behavior)).

## 5. Limitations (Non-Goals)

- **An orphaned footnote — declared in `word/footnotes.xml` but never referenced by any `w:footnoteReference` in the body — is intentionally excluded.** Population is driven entirely by anchors found in the body (see [Output Schema](#3-output-schema), [ADR-0004](../../../docs/adr/0004-phase-3-footnote-module-and-shared-anchor-resolution.md)); this is also why Word's own boilerplate separator/continuationSeparator footnotes (`w:id="-1"`/`w:id="0"`, present in essentially every real `word/footnotes.xml`, never referenced from the body) never appear here without any explicit `w:type` filtering — they simply never have an anchor. A caller that needs to detect an orphaned footnote's existence must inspect `word/footnotes.xml` itself; this tool does not surface it.
- **`paragraph_index` addresses only top-level body paragraphs**, identical to `get_structure`'s scope (see [specs/get_structure.md §5](get_structure.md#5-limitations-non-goals)): a footnote anchored inside a table cell is not represented here, matching `get_structure`'s footnote-anchor index, which has the same gap.
- **Endnotes are not surfaced.** `word/endnotes.xml`/`w:endnoteReference` are a structurally distinct OOXML part and element this tool does not read — the whole tool surface only covers footnotes (see [README.md](../../../README.md#available-tools), [specs/read_document.md §5](read_document.md#5-limitations-non-goals)).
- **A `w:tbl` inside footnote content is not rendered.** Only a footnote's direct `w:p` children contribute to `content`; OOXML technically permits a table inside footnote content, but this tool's content rendering only ever walks paragraphs (consistent with `get_structure`'s own "nested tables are not extracted" boundary for table cells, see [specs/get_structure.md §5](get_structure.md#5-limitations-non-goals)). Such a table's text is silently absent from `content`, not an error.
- **List numbering is not computed** — same as [specs/read_document.md §5](read_document.md#5-limitations-non-goals).

## 6. Formatting & Safety Guarantees

- Read-only, same as `read_document`/`get_structure` — never opens the target file for writing.
- `path` is resolved and validated against the allow-listed roots, and a UNC network path rejected, before the file is opened — identical to [specs/read_document.md §6](read_document.md#6-formatting--safety-guarantees).
- Every internal XML part this tool reads — `word/document.xml` **and now also `word/footnotes.xml`** — is parsed with the same hardened `lxml` parser (`resolve_entities=False`, `no_network=True`) as every other tool, so a crafted external entity in either part cannot read local files or trigger network access (see [ADR-0001](../../../docs/adr/0001-ooxml-library-and-module-layout.md), [docs/security-model.md §4](../../../docs/security-model.md#4-input-validation), which already named `word/footnotes.xml (Phase 3)` as a covered part in advance).

## 7. Error Behavior

| Case | Behavior |
| --- | --- |
| `path` escapes all allowed roots / no allowed roots configured / UNC network path | Identical to `read_document` (see [specs/read_document.md §7](read_document.md#7-error-behavior)). |
| File does not exist, is not a file, is not a valid ZIP, exceeds the size limit, or is missing/malformed `word/document.xml` | Identical to `read_document` — these checks are shared, unchanged logic. |
| `word/footnotes.xml` is missing | Not an error. If the body has no footnote anchors, `footnotes: []`. If the body has one or more anchors (a malformed/inconsistent document), every anchor still appears, each with `content: null`. |
| `word/footnotes.xml` is present but malformed XML | Rejected with a clear "not a valid .docx file: malformed XML in word/footnotes.xml" error — a `.docx` that declares the part but corrupts it is treated as invalid, the same posture `get_structure` takes for a malformed `word/styles.xml` (see [specs/get_structure.md §7](get_structure.md#7-error-behavior)). |
| An anchor's `id` has no matching `w:footnote` in an otherwise-valid `word/footnotes.xml` | Not an error for the call as a whole — that entry's `content` is `null`; other entries are unaffected. Mirrors `get_structure`'s handling of a referenced-but-unresolvable style id, which falls through rather than failing the whole call (see [specs/get_structure.md §3](get_structure.md#3-output-schema), step 3/4). |
| `word/footnotes.xml` contains a DTD declaring an external entity | Parsed successfully; the entity reference is never resolved (same guarantee as `word/document.xml`, see [specs/read_document.md §7](read_document.md#7-error-behavior)). |

## 8. Test Coverage

Reference: `tests/test_footnotes.py` (functional and error/edge at the `get_document_footnotes` level, including XXE hardening for `footnotes.xml`), `tests/test_get_footnotes_tool.py` (contract, functional, error/edge at the MCP-protocol level), `tests/test_security.py` (path sandboxing, shared), `tests/integration/test_footnotes_consistency.py` (cross-tool checks against `read_document` and `get_structure`).

- **Contract:** tool discoverable via `list_tools`; name, description, input schema, output schema, and version (`_meta`) match this spec.
- **Functional:** against `tests/fixtures/footnotes.docx` (three footnotes: two anchored in the same paragraph, a third in a different paragraph) — correct `id`/`paragraph_index`/`content` for all three, correct ordering, the same-paragraph pair both present and not collapsed into one entry; against `tests/fixtures/minimal.docx` (its existing single footnote) for the simple baseline case; a synthetic multi-paragraph footnote (content joined by `"\n"`).
- **Error/edge:** path outside allowed roots; oversized file rejected before parsing, file at exactly the size limit accepted; missing `word/footnotes.xml` with zero body anchors (`footnotes: []`); missing `word/footnotes.xml` with a dangling body anchor (`content: null`); malformed `word/footnotes.xml` (hard error); an anchor id with no matching declared footnote in an otherwise-valid `word/footnotes.xml` (`content: null` for that entry only); the Word boilerplate separator/continuationSeparator footnotes (`id="-1"`/`id="0"`) never appearing in the output; unicode and astral characters in footnote content; XXE-crafted `word/footnotes.xml` (external entity not resolved).
- **Cross-tool consistency:** `get_footnotes`'s `id`/`paragraph_index` pairs match `get_structure`'s footnote-anchor index exactly, and every `id` matches a `"[^id]"` marker at the same paragraph in `read_document`'s output — checked against both `minimal.docx` and `footnotes.docx`.

## 9. Examples

Against `tests/fixtures/minimal.docx` (see `tests/test_get_footnotes_tool.py::test_call_get_footnotes_on_minimal_fixture_resolves_the_single_footnote`), with `DOCX_MCP_ALLOWED_ROOTS=/workspace`:

Request:

```json
{ "path": "/workspace/reports/minimal.docx" }
```

Response:

```json
{
  "footnotes": [
    { "id": "1", "paragraph_index": 2, "content": " This is a footnote." }
  ]
}
```

`content` carries a leading space: that is the literal text Word itself writes into the footnote's text run right after the auto-number, preserved verbatim (`xml:space="preserve"`) rather than trimmed — a caller comparing `content` against `expected_content` in a following `edit_footnote` call must include it. Against `tests/fixtures/footnotes.docx`, which anchors two different footnote ids in the same paragraph, `footnotes` would instead contain `{"id": "1", "paragraph_index": 2, ...}` and `{"id": "2", "paragraph_index": 2, ...}` as two separate entries — never collapsed into one — plus a third, `{"id": "3", "paragraph_index": 4, ...}`, in a different paragraph.
